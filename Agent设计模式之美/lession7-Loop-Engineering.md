# 热点加餐｜Loop Engineering：如何把 Agent 的循环工程化

> Loop Engineering 就是 Harness，就是工程化本身。

## 导言

今天的分享认知负载比较大，因为概念、名词比较多。先说 **Loop Engineering 到底是什么**，把概念说得明确一些，让大家都在一个平面上去理解问题。

我们从一个假想的微信小程序入手——**"到店吧"**。

以前的小程序都是我们自己点：你要什么选单，比较自己喜欢的商品，下单，确认。现在我们让 Agent 给我们推荐，我就一句话：**"给我找到附近的比较人气旺的外卖，想吃水饺"**，你就跟它一说，这个 Agent 自己负责给你去从微信小程序生态中寻找发现。

微信在未来三五个月、一两年之内遍地都是的小程序生态里，其实开放了 Agent 平台和生态，以后它的小程序都是一大堆的 Agent Service，或者一系列的 **Skills**，供你随时调用。

## 一、Loop Engineering 到底是什么

### 工程师的新能力象限

这非常重要。我最大的读者群，上来都会问："朋友你是什么技术方向？"一半的人说："佳哥，我是 Java 后端。" Java 后端现在进入了 Agent 时代，学习 Agent 的朋友最多。我们从能力象限的角度，是要往哪个方向过渡？

- **传统的硬技能**该保留的保留：代码、软件工程、调试、架构的权衡，这些站在过去程序设计理论基础上的东西，仍然在这个时代相当重要。
- 从**竖轴**上看，你是逐渐从**写代码过渡到搭建系统的能力**
- **传统的软技能**永远需要，现在更需要：需求的理解、业务的建模、团队的沟通，这些是我们现在最强的护城河
- 从**横轴**上看，是从**执行到设计的技能**，包括规约的表达、验证的设计，尤其是评价体系的搭建

> 以前我搭建一套 Evaluation 体系，只是给自己测评用。现在我搭建出来的 Evaluation 体系，不仅给我用，给团队用，更重要的是给未来越来越聪明的 Agent 来用。

**这就是为什么我要强调 SDD（规范驱动开发），强调验证的设计，强调 TDD 测试驱动的开发，强调 Evaluation 体系的搭建，它是一举多得。**

### 三本经典著作的哲学底座

为什么我们现在越强调让 Agent 自主循环 Loop，能够出现越来越多的智能涌现？

1. **凯文·凯利《失控》** —— 他所说的造物九律，九个自然规律，其实就是和 Loop Engineering 和 Agent 的循环每天所做的事相当类似
2. **侯世达《哥德尔、艾舍尔、巴赫》（GEB）** —— 提出来怪圈和智能的涌现是怎么一回事
3. **《有限与无限的游戏》** —— 帮助我们思考这个循环的边界在哪里

## 二、从热词演进看 Loop Engineering 的定位

实际上我认为它仍然是 **Prompt Engineering**，但有一个区别——**它的关注点在变化**。

当我们做 Prompt Engineering 的时候，关注的是**对模型一次调用的结果**。经过 **Context Engineering**，也就是对上下文窗口的提炼和构造，落到设计模式里叫感知模式的设计，你把模型最需要的东西传递给它。那么到了 **Loop 和 Harness Engineering** 这个层次，你关注的是**整个循环**，多次调用，不断重复调用模型，要求在自我重复迭代很多次之后达到一个好的结果。

> **一句话讲透 Loop Engineering：你不再一句句手动写每一个 Prompt，而是写一个程序，或者说设计一套循环，让这套循环替你去 Prompt。** 以前是自己一步步干，现在是 Agent 有一个目标，它就在行动、观察、判断，再继续行动，什么时候收手，在循环的过程中停止。

**主语变了。**

- **以前**：我做 Prompt，模型给我答案
- **现在**：整个系统做 Loop，我得到一个结果，我不再手动调试任何 Prompt，我只是去设计不断给模型 Prompt 的循环

**价值的单位也发生了改变。**

- **以前**：模型给我的回答结果有价值
- **现在**：我不太在意模型一次是不是做对，它可以做错，关键在于我能不能通过循环定位问题。**从错到对，不断循环完成任务的轨迹，变得比一次答对更重要**

> 因此我认为 Loop Engineering 其实就是我们一路以来所说的**工程化本身**。它从第一天开始就没有创造新概念，它就是 **Harness Engineering**，也就是我们一直给大家讲的 Agent 设计模式：怎么操控上下文、怎么调用工具、怎么管理记忆、怎么做对模型的治理、怎么把 Agent 变成一个很强、很可控、能够上线交付的系统。

**所以 Loop Engineering 就是 Agent 设计模式的工程化落地过程。模型早就不再是瓶颈，瓶颈在于这个循环的设计。**

## 三、《失控》的造物九律与 Agent 循环

为什么《失控》这本书里提出来的判断越来越精准？凯文·凯利在 1994 年写的这本书，他说**人造物越来越像生命体，生命体变得越来越工程化**。

他提出的**造物九律**，和 Loop Engineering 逐条对应：

| 序号 | 造物九律 | 与 Agent 循环的对应 |
|------|---------|------------------|
| 1 | **分布式状态** | Agent 时代我们有多 Agent、子代理分布式的状态 |
| 2 | **自下而上的控制** | 机械平面的自治和固定工作流的编排 |
| 3 | **递增的收益** | 复利效应。企业积累的技能越多，Agent 就越强 |
| 4 | **模块化生长** | 生命体会模块化往上生长 |
| 5 | **边缘部分越来越大** | 创新常常不在中心地带产生，越是有动荡、放的部分，系统就越有生命力 |
| 6 | **礼待错误** | 设计模式里有一个特别的模式叫失败日记。出错就是你未来避免类似错误发生的必要条件 |
| 7 | **不要求最优** | 目标众多，不追求单一的最优解，因为单一的最优解往往很脆弱（反脆弱） |
| 8 | **持续的不均衡状态** | 生命系统的活力在变化、张力、扰动中存在 |
| 9 | **变自生变** | 变化本身来自于变化 |

> **通过不断积累技能、沉淀技能，下一轮的 Loop 就变了，跑在我之前积累的 Skills 上面再去重新 Loop 就不一样了。** 我每 Loop 多一次，我的企业、我个人就多了一个 Skill。

比如说我们科研单位正在开发科研智能体，现在很简单，有一套系统、一套规矩，所有科研人员跟着这套规矩做科研，所有对话都在系统中发生，所有结果都被记录。**三个月之后，几千个科研人员每天的科研对话，系统就可以开始沉淀，提炼 Skills，系统加上科研人员就可能越来越会做科研。从第一天积累也是很重要的，不积累，两年之后还是从零开始。**

## 四、从一个用户旅程开始

### 执行型 vs 内容生成型 Agent

用户需要做的很简单，他说好了，今天订两个人的火锅，细节不管，150 块钱之内就行。这就是小程序收到的全部内容。

这句话背后一套旅程就开始了——先帮他找到合适的门店，比较套餐看哪个划算，下单、支付，最后出票。**这就是我们所说的执行型 Agent 的承诺，它要跑通一套真实的任务。**

所以这是第一个关键概念——

> **执行型 Agent 不是对话聊天型的 Agent，不是内容生成型的 Agent。**

什么是内容生成型 Agent？给我做个报告，没有对错，它怎么 Loop、怎么多次之后，反正给你一个东西，你打 10 分就是 10 分，打 8 分就是 8 分，那个东西没有标准。

**但是执行型 Agent，如果我下了单，它给我付错了钱，我是要投诉的、要索赔的。** 所以这种东西跟让它给我做个研究报告完全不同。

### 最小闭环 vs 真正的产品循环

**最小闭环就是一个 ReAct：** 想、做、看，做不好再想、再做、再看，直到完成了就搞定。这就是我们做 Demo 做到这个程度就可以了。

**但是在真正的执行型任务上，没有一个产品能够通过这样一个最小 ReAct 循环就完成，这是不可能的。**

在真正的产品中，这种循环会崩盘在多个节点：

- **模型跨步漏步**
- **参数漂移**
- **虚假成功**：Agent 有时候也是讨好型人格，它内部已经失败了，不知所措了，最后跟你说已经成功完成了，等着吃饭吧
- **死循环**：一直调 API 一直调不到，停不下来
- **上下文爆炸、失控**

> **这种循环如果没有控制，你其实是在把整个程序的设计交给运气。**

### 解决方案：把工程化循环在每一个环节明确管控

执行型 Agent 的难度。内容生成型的你可以不去调试，做得不好再给一些额外 Prompt，它下一次真的做得更好。**但执行型 Agent 的结果更重要。**

解决方案就是把工程化循环在每一个环节需要明确管控的地方，全部进行治理：

- 该**感知**的东西要给
- 该**记忆**的失败日志要记
- **行动轨迹**要存档
- 每一步的**思考和行动调用工具的过程**都要用可观测性呈现出来
- 每一步**机械状态**的进展都要记录下来
- **治理和停止条件**：出错怎么 Rollback，死循环怎么停止，都需要详细设计

## 五、认知地基与设计地图

### 三个平面：叙事平面 + 控制平面 + 调度平面

> 这个过程需要把**控制平面和叙事平面拆分开**，这就是我们所说的**二元论**。

- **叙事平面**：自然语言、语义、人话的东西，存储在一个地方
- **控制平面**：离散信号，要么对要么错，要么是订单 ID 要么是其他订单的 ID，控制程序分支往哪个方向走

以前做系统架构你可能只有机械控制平面，不需要考虑叙事。这完全是在 Agent 大模型时代出来之后才有的。

> **未来的架构是叙事平面和控制平面二者的有机结合。** 叙事平面负责发散，负责很多未来的可能性，我在这个平面进行 Loop 才有意义，它不断变化，因为是自然语言的叙事、大模型思考推理的结果。控制平面负责收敛，把你说的一大堆东西收敛到离散信号里去驱动，你要调哪个美团的订单服务，得真正把东西给人家买了。

再衍生出来第三个平面——

- **调度平面**：Workspace、Orchestrator，各个节点的状态，工作流程执行到哪里了

**一个 Agentic Workflow 的循环是通过叙事平面、控制平面、调度平面三个平面相互配合，才能够产生完整的 Loop 结果。**

### 双轴框架在 Loop 中的应用

再说到 Agent 设计双轴框架，通过认知功能和执行拓扑进行组织。这是 Loop Engineering 整体框架中的一套共同语言。在设计每一个 Loop 工程节点的时候，我都需要思考可以复用什么方面的设计模式。

**失败日记模式的例子：**

> 当我订餐给我订来了某个店，我很生气，除了他家啥都行。Agent 没错，但我给了差评。**这个失败相当有特色，针对我这个 ID，以后下单的时候千万查一查附近的鼎泰丰，口碑再好也排除出去。** 这就是一次成功的经验记录。

**治理模式的例子：**

> 到店吧小程序付款需要用户确认，走到**审批门模式**。产品经理可以递要求说不可超过两次审批门，因为我就是为了跟它说我要吃包子，20 分钟后吃到，不要让我再点超过 3 次。**在这个约束下，设计 Loop 的人就说，人审批不可以超过 3 次，付钱时加一个审批，确认买包子可能加一个，最多两次。**

## 六、把 Loop 工程化

基础理论讲完了，储备知识搞定了，我们就进入工程。现在要设计到店吧这个 App，在每一个层次中都需要设计什么？

### 四层运行时架构

```text
用户入口层    （从小程序发起委托）
    ↓
协议层        （意图识别、小程序 MCP 连接、Skill 选择和策略路由）
    ↓
能力层        （各种 Skills、MCP、原子接口、原子组件、结构化的数据和 UI 渲染卡片）
    ↓
状态治理层    （编排器、Workspace、DAG 图、机械状态平面储存、Payment、可观测性 Tracing）
```

### 循环入口：从自然语言到机器语言

**怎么把"订火锅 150 块钱"转成机器语言？** 我需要把它收敛成离散的控制信号：

```text
Task:           BuyFood
FoodCategory:   火锅
Budget:         150
Time:           今晚 6 点到 9 点
ConfidenceLevel: 0.93
```

你实现了**从模糊自然语言到精确意图识别的收敛过程**。

### 调度大脑 Orchestrator

意图网关路由判定搞定了之后，就到了 ReAct 推理行动的第一步。然后是**调度大脑 Orchestrator** 的设计：

- 用户消息先到 **MessageHandler**——收消息、展示结果，不负责业务解决
- **Orchestrator** 是真正干活的人——拿到意图识别给出来的控制信号，交给 ReAct 去做事、编排下游链路

> **如果某一步做错了，Orchestrator 不会从头再来，它对流程都有记录，会按状态机回滚到最后的断点再重试。**

### 机械状态平面 · Provenance 坐标

在这个过程中最重要的核心思路，就是**机械状态平面的设计**。

每一个 ID 和任务数据结构都要清晰地存储在状态平面中，供审核、供调用：

- User ID
- Store ID
- 电话、地址
- SKU ID
- Cart
- Coupon ID
- Payment Session
- Order ID
- Ticket

**这些全都是最重要的机械状态信息，每一个都不可以出错。**

> **记住，参数的记录和传递不能完全交给模型。确定性的值必须由程序进行机械掌控。**

每一个参数都需要有可审计的来源，这个叫 **Provenance 坐标**：

- 所有的参数哪来的？
- 订单 ID 谁生成的？
- 什么时候生成的？
- 传给哪个小程序了？

> 越是在 Agent 时代，我们让它自己一直 Loop，这些可以留下的痕迹，对于 Agent 到底做了什么、怎么做的、调用了谁，是非常重要的审核来源。

### 任务状态机

**任务状态机也是关键。** 每一个委托都是一次有状态的节点，能够被追踪、被回退、可以验收。某一步失败需要回退多少，这些都需要在设计工作流时设计出来。

到了一定程度输出一个原子卡片：

- 门店卡片
- 套餐对比
- 订单确认

如果产品经理说不能让用户确认太多次，就把几个原子卡片集成起来，用户点一下就行。

### 设计思想：让计划活在代码里，让创意活在上下文里

到店吧这个小程序，我更愿意让它**生活在代码里**，因为最重要的事，别把人家订单搞错了，不要让人家买包子你回来给人家饺子。

但**科研场景就不同**，可以给更多灵活性，让它更多**生活在上下文和积累的 Skills 里**，有可能发现更多新的灵感和东西。

### 循环的护栏

循环的护栏就是这些，**该支付的时候必须有用户确认，加一个支付的审批门**。

### 全程轨迹观测 · 手表背面比喻

最后是全程轨迹观测，要透明：

- 一次对话，LLM 调用了什么
- 意图网关路由走到哪个值
- 选店、选套餐、选优惠的环节
- 调用的是哪个 Skill、哪个 MCP
- 推理和行动的结果是什么
- 一共几步
- 工具调用怎么个情况

**全部一清二楚。这是给开发人员的可观测的玻璃罩。**

**梁博老师有一个很好的比喻：**

> **我们有一个手表，正面是客户看到的清清楚楚的结果，给你一个包子，套餐就是 20 元。但把手表翻过来，背面是一大堆齿轮和机械步骤，很多工具啮合在一起，非常复杂。这就是循环的每一步到底怎么走的。**
>
> **用户看到很清晰的界面，这是手表正面。我们程序员看到的东西，是大模型的思考平面、控制平面、ID 和工具调用的各个环节，全部都在玻璃罩后面呈现。**

## 七、Loop 的边界与灵魂

### Loop 的安全边界

**Loop 的安全边界要有数。**

- 什么东西工具可以读
- 什么写操作要注意隐私、支付、模型不确定性的东西

### 边界和停止条件是循环本身的一部分

**Loop Engineering 的另一个灵魂，就是你 Loop 的边界在哪里？边界和停止条件是循环本身的一部分。**

支付场景的边界比研究场景严格得多。研究场景越发散越好，灵感来自于系统的不确定性和动荡。但做支付、做企业级 SaaS，就没有这么多灵活性。

### GEB 怪圈理论

说到 **GEB** 这本书，它的主题是怎么样通过无意义的符号涌现出意义和"我"。人工智能大模型不就是通过一圈一圈的循环神经网络、Transformer 不停迭代，涌现出来了一些让我们觉得是强人工智能的意义嘛。

> **怪圈理论告诉我们，不要在循环过程中自己给自己打分。对循环本身的验证，必须来自于循环的外部。**

在 Agent 场景中，可以通过机械平面的真值去验证，用户真实地去验证，或者换成另一个模型去验证，用 Claude 和 GPT 相互校验，因为它们是通过不同数据训练出来的，品味和想法还确实可以互相提高。

### 有限与无限的游戏

《有限与无限的游戏》把世界上一切活动分成两种游戏：

- **有限游戏**：在边界内玩，有规矩，有终点
- **无限游戏**：边界外边玩，规则由自己定义，没有终点，可以一直玩下去

> **这本书的精华就这么一句话：有限的游戏是在边界内玩，无限的游戏玩的就是边界。**

换成我们这一单火锅——

- **一单火锅就是一个有限的游戏**，你只能在他附近有限的选择中选最好的一次
- **但如果把这个东西看成一个循环的生态，它就是一个无限的游戏**。你的 Agent 越来越了解主人今天想吃啥、明天想吃啥、后天不想吃啥、啥时候吃火锅吃烦了

这个 Loop 不需要局限在这一单火锅本身，下一单呢？那就是另一个事了。

> **如果你认为这是一个无限的游戏，你的 Agent 可以变得越来越聪明，到最后都不用主人说，它知道每天下午 6:30 自动给他订火锅。**

### 哪些场景值得上比较重的循环？

看你是**执行型还是内容型**，是**单步 Agent 还是长程任务组合**。

> **执行型 × 长程组合，两个轴都过了才值得。**

## 总结

今天的几个重点判断：

1. **Loop Engineering 就是 Harness，就是工程化本身**
2. **先分执行型和内容型**
3. 模型的思考是**叙事平面**，机械的执行是**控制平面**
4. **机械状态平面的数据准确性、Provenance 是重中之重**
5. **计划活在代码里，不是由上下文束缚**
6. 要有清晰的**有向无环图**
7. **边界和停止条件是循环本身的一部分**
8. **用无限游戏的心态去设计有限游戏的边界**
