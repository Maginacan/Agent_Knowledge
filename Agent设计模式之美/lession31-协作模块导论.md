# 31｜协作模块导论：人一多，就需要把边界说清楚

> **核心命题**：单个 Agent 的上下文和注意力有限，复杂任务常常需要几位执行者一起完成。协作模式要回答的是——**当工作跨过执行者边界时，怎样把意图、真值、结果和责任说清楚，让局部产出真正合成为一个可验收的整体**。
>
> **一句话**：协作模块要解决的不是"分派任务"，而是"意图随消息，真值随引用，结果随工件，责任随验收"。
>
> 多 Agent 不是更高级的默认架构。它要先回答"为什么值得拆"和"拆开以后能不能安全运行"两件事，再决定是否启用。

---

## 一、释题：半局棋合起来

> "分身各赴诸端事，合意同归半局棋。"

假设要做一页"2026 年多 Agent 框架选型简报"，把任务同时交给三位研究员：

- 三人都很认真，但拿到的结果是同一块内容的三个版本（都在比较 CrewAI 和 LangGraph）。
- 相互之间怎么分工，没人管。
- 状态怎样保存，没人查。
- 三人怎样交接、如何协作，没人负责。
- 最终简报要覆盖哪些方面、是否形成统一且有高度的整体思想，没人在意。

问题就出在：Agent 之间的任务范围重叠了，内容留下空白，最后又没有人按总目标验收。

这就是协作模块要解决的问题：**当工作跨过执行者边界时，怎样让局部产出真正合成为一个可验收的整体**。

多 Agent 是这套协作机制的一种实现形式。人 + Agent 混合协作、两个外部 Agent 系统之间的合作，也会遇到同样的问题。

---

## 二、到底什么算 Agent 协作

开场案例的真正问题，是系统只复制了一个目标：

> 研究 2026 年多 Agent 框架。

它没有继续说明：

- 你负责哪一块？
- 哪些内容不在你的范围内？
- 依据哪一版资料？
- 最后交回什么？
- 谁检查三份结果是否完整？

于是，三位研究员都选了最容易进入的方向。对每位来说，选择完全合理；对整份简报来说，三个合理选择叠在一起，留下了两块无人负责的空白。

### 区分两种"完成"

| 类型 | 含义 |
| --- | --- |
| 局部完成 | 某位研究员已经返回了一份材料 |
| 整体完成 | 所有必需内容已经覆盖，重复和冲突得到处理，最终结果通过了总目标验收 |

很多多 Agent 系统只记录第一种完成：只要所有子 Agent 都返回，父任务就进入 `completed`。至于大家有没有做重、有没有漏项、结果能不能拼起来，系统留给最后一个大模型。

这更像同时发起了几次调用，还谈不上协作。一个 Agent 连续调用搜索、数据库和代码工具，仍然是**一位执行者在使用多种能力**；一个 Agent 加载三份 Skill，也没有因此变成一支团队。

协作模式讨论的是：多个相对独立的执行上下文怎样围绕同一个目标工作。这里的"相对独立"，至少意味着它们在**上下文、工具、状态或责任**中，有一项被明确分开。它们可以使用同一种模型，也可以来自不同模型、不同 Harness，甚至由不同公司的系统承载。

### 工程化定义

> **Agent 协作**，是把一个共同目标分配给多个相对独立的执行上下文，再通过明确的边界协议把局部结果组成一个可验收的整体。

这句话包含三个动作：**分出去、做回来、验整体**。

- 只会分出去 → 系统得到的是一群各自宣布完成的 Agent。
- 没有隔离 → 几位 Agent 看似分工，实际上仍共享同一段嘈杂上下文、同一套宽泛工具和同一份可变状态。
- 只验局部，不验整体 → 就会出现开场的情况。

## 三、协作契约：意图、真值、结果和责任

工作留在一个 Agent 内部时，很多信息藏在上下文里：它知道为什么排除某个方案，记得当前用哪一版资料，也知道自己还欠哪一步。

一旦工作跨过边界，这些隐含信息就靠不住了：

- 接收者可能只拿到一句"继续完成简报"，不知道目标读者、任务范围和已排除的方向。
- 关键数字经过几轮自然语言转述，可能混入旧值。
- 上游觉得自己已经交付，下游却认为自己只是临时帮忙。
- 最后出问题时，其实无法追责。

因此，协作开始前，要先立一份四句话的**边界契约**：

> **意图随消息，真值随引用，结果随工件，责任随验收。**

### 1. 意图随消息

任务消息要说明这一棒**做什么、做到哪里**，以及**哪些事情明确不在范围内**。

更清楚的任务应该是：

- **Atlas**：研究团队怎样组织和委派任务。
- **Birch**：研究上下文、会话和状态怎样隔离与保存。
- **Comet**：研究结果怎样在 Agent 或系统之间交接。

### 2. 真值随引用

关键事实不要在 Agent 之间反复口头转述，应当指向：

- 原始记录、官方文档、代码版本、数据库快照或 commit。
- 内容经过压缩，事实仍然能回到原处核对。

任何协作里都要回答：

- 隔离的是会话、工具还是文件系统？
- 结论针对哪个 provider？
- 依据哪一版文档或代码？

### 3. 结果随工件

Worker 不应只返回一段自由文本：

- 研究任务 → 提交资料卡。
- 代码任务 → 交补丁和测试结果。
- 审批任务 → 交版本化决策记录。

一张最小研究卡应包含：

- **责任面**：谁负责哪一块。
- **结论**：本块给出的判断。
- **适用范围**：结论在什么条件下成立。
- **来源**：依据哪些原始材料。
- **版本**：依赖哪一版资料/代码/数据库。
- **未决问题**：还有哪些事项需要进一步求证。

主 Agent 拿到的是**可以检查、比较和组合的工件**，不必重新阅读每位 Worker 的完整对话。

### 4. 责任随验收

接收者依据明确标准签收以后，这一项责任才算真正交付。验收要回答：

- 谁接收了？
- 接收的是哪一版？
- 依据哪套标准？
- 通过、退回还是等待补充？
- 下一步由谁负责？

### 落到三类核心对象

| 对象 | 作用 |
| --- | --- |
| 任务卡（TaskCard） | 固定意图和范围 |
| 结果工件（ResultArtifact） | 携带结论、来源和版本 |
| 验收回执（AcceptanceReceipt） | 说明谁接收了什么，以及父目标是否可以继续 |

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class TaskCard:
    task_id: str
    goal_ref: str
    owner: str
    scope: str
    input_refs: tuple[str, ...]
    deliverable: str
    acceptance_ref: str

@dataclass(frozen=True)
class ResultArtifact:
    task_id: str
    producer: str
    artifact_ref: str
    evidence_refs: tuple[str, ...]
    version: str
    content_digest: str

@dataclass(frozen=True)
class AcceptanceReceipt:
    task_id: str
    artifact_version: str
    artifact_digest: str
    reviewer: str
    accepted: bool
    reason: str
```

这几个对象负责让系统知道：**现在谁在做什么，依据什么，交回了哪一版，最终有没有被接收**。

## 四、什么时候才值得协作

多 Agent 不是更高级的默认架构，它是在支付**通信、调度、等待和聚合**成本以后，换取**并行、隔离、专业分工和独立视角**。

因此，决定是否协作时，要把"为什么值得拆"和"拆开以后能不能安全运行"分开。单一智能体已经完全可以解决问题时，就不要强行引入多智能体架构。

下面四类情况出现时，再开始考虑协作：

1. **任务中存在真正互不依赖的工作面**：不同资料源、地区、合同、代码目录或测试分片可以同时推进，并行能够缩短墙钟时间。
2. **过程信息已经超过一个上下文适合承载的范围**：子 Agent 可以把大量搜索、阅读和局部尝试留在自己的上下文里，只把压缩工件交回主管。
3. **权限或专业责任需要分开**：研究员可以读取资料，发布者才有官网写权限；对账 Agent 可以查看工资事实，付款 Agent 才能调用银行接口；安全、财务和法务也可能需要不同的工具、资料与验收标准。
4. **独立视角本身有价值**：同一个方案需要第二证据源、专职评审或竞争假设时，另一个执行者带来的价值不是速度，而是不同的观察条件。

这些是采用协作可能获得的收益，**并不保证协作一定会成功**。真正启用多 Agent 之前，还要过三道门槛：

| 门槛 | 要回答的问题 | 开场案例中的检查 |
| --- | --- | --- |
| 任务可拆 | 能否拆成责任清楚、可以单独验收的子任务 | 拓扑、状态和交接是否各有明确负责人 |
| 状态可管 | 上下文、工具和工作区能否隔离，或写入能否串行收口 | 三位研究员可以独立阅读，最终稿只由主编修改 |
| 结果可验 | 局部工件能否对齐、组合并接受整体验收 | 三个方向是否到齐，是否重复，来源是否可核 |

### 16 个 Agent 写 C 编译器

Anthropic 曾让 16 个 Agent 一起写一个 C 编译器，最终产出约 10 万行 Rust 代码，还能编译 Linux 6.9。它之所以跑得起来，**不是因为 Agent 多，而是任务可以拆开**：不同 Agent 负责不同部分，各自有测试，Docker、Git 和 CI 又能防止大家互相踩脚。

可当 16 个 Agent 都卡在同一个 Linux 内核错误上时，并行反而失效：大家反复排查同一个问题，还会覆盖彼此的修改。后来，团队用 GCC 作为正确结果的参照，再把问题重新切成能够单独验证的小块，并行才重新发挥作用。

> **多 Agent 不是人越多越快**。任务要能拆开，工作区要能隔离，结果还要能独立验收。

### 多个 Agent 写代码

只要每个人有独立的 worktree、容器或沙箱，再配上任务锁、合并规则、自动测试和发布门槛，并行写入完全可以做。问题是，这些东西一个都不能少。否则只是把一个人的写权限复制成了十份，冲突也跟着放大。

判断协作是否划算，要算清楚账单：**并行省下来的时间和带来的质量提升，能不能抵掉多出来的通信、协调和聚合成本**。先跑一个单 Agent 基线，再比较结果质量、总 token、实际耗时、重复工作、交接出了多少问题、以及最后真正通过验收的比例。

### 并行的天花板

十个人可以同时查资料，最后还是要有人把材料合起来、统一口径、处理冲突并做最终决定。前面跑得再快，最后这个收口环节慢，整体也快不到哪里去。

### 几类场景的协作拆分思路

| 场景 | 怎样拆 | 判断 |
| --- | --- | --- |
| 开放式行业研究 | 按地区、公司或资料源分头检索，由主编统一成稿 | **适合**。工作面相对独立，读操作多，来源还可以交叉核对 |
| 八百份合同初筛 | 每个 Worker 只读一份合同并提交风险卡，聚合器检查漏评、重复和冲突 | **适合**。输入天然分片，上下文和权限都容易隔离 |
| 修复一个文件里的状态机 Bug | 多人共享同一段隐含控制流，还需要同时修改同一文件 | **先克制**。单 Agent 配测试循环通常更连贯 |
| 月末付款 | 对账与异常核查并行，真正付款只保留一个入口 | **混合使用**。判断可以并行，写入和放行集中 |
| 跨团队内容风控 | 多个检测 Agent 按事件独立运行，案件结束需要统一终止条件 | 规模足够大时再考虑编舞，并先补齐事件追踪和治理门 |

## 五、协作模块中的四个模式

层级委派、扇出聚合、对抗评审和交接链，这四种模式，分别在协作链的不同位置修补不同问题。

| 模式 | 边界 | 作用 |
| --- | --- | --- |
| 层级委派 | 谁负责哪一块，主管怎样保留总目标 | 把简报拆成拓扑、状态和交接三张互补任务卡 |
| 扇出聚合 | 多路结果怎样带着口径、来源和冲突返回 | 检查三块是否到齐，识别重复资料和相互矛盾的结论 |
| 对抗评审 | 谁有权提出异议，异议怎样影响放行 | 防止主编把有限结论改成没有证据支持的绝对标题 |
| 交接链 | 状态、证据和责任怎样交给下一棒 | 让事实核查后的版本准确到达编辑和发布者 |

### 层级委派：把人头变成责任

开场失败的第一处断点在**派工**。主管要拆出三份互不相同的责任：Atlas 负责拓扑，Birch 负责状态，Comet 负责交接。每张任务卡都写明问题、输入、交付物和验收标准。

主管派完工以后仍然保留总目标。三位 Worker 分别完成自己的局部责任，整份简报有没有完成，仍由主管检查。

子代理隔离是层级委派的一个伴随机制。层级委派回答"这块责任交给谁"，子代理隔离回答"这位 Worker 在什么边界里工作"：它能看到哪些上下文，使用哪些工具，拥有多少预算，失败会影响多大范围。

### 扇出聚合：不要急着把差异抹平

任务拆开以后，结果还要收回来。三位研究员可能讨论不同维度，也可能引用同一份资料，还可能得出冲突结论。聚合器要：

1. 统一对象和口径。
2. 识别同源重复。
3. 保留未决冲突。
4. 最后检查这些局部结果合在一起是否违反全局约束。

在技术简报中，聚合器会发现：

```text
topology:    已覆盖
state:       已覆盖
handoff:     已覆盖
重复责任:     0
核心来源:     可追溯
未决冲突:     1
```

多路工作到齐，只能说明材料齐了。**结论能不能成立，还要看来源和冲突怎样处理**。

### 对抗评审：让异议进入放行条件

聚合后的报告仍然可能被主编概括过度。比如，资料只证明进程内 Worker 的会话隔离，标题却写成"所有子 Agent 默认完全隔离"。

这时，评审者要提交**带规则和证据**的异议。提案权、举证权和裁决权由不同责任主体承担，评审可靠可信。

### 交接链：把正确版本交给下一棒

研究、事实核查、编辑和发布通常由不同角色顺序完成。可靠交接不能只传一段前情摘要，而要传递一份**版本化交接包**，其中包含：

- 当前目标。
- 已确认事实。
- 工件引用。
- 被排除项。
- 下一步责任。

接收方签收以后，责任才真正转移。

## 六、Harness 会变，协作边界不会

下面看业界实践。这些框架能够帮助我们创建子 Agent、转移会话、限制工具和传输 Artifact。但它们**不会自动知道**简报需要覆盖哪三块，也不会自动决定谁有资格宣布整件事完成。

也就是说，它们只能帮助我们搭建起基本的协作协议框架，而具体的协作责任（业务契约），都需要在实践中补充。

| Harness / 协议 | 边界和接口说明 |
| --- | --- |
| CrewAI | Crew 负责角色协作，Flow 负责状态和流程；层级流程中的 manager 承担委派与验证 |
| OpenAI Agents SDK | 区分 agents-as-tools 与 handoff，明确工作委派和控制权转移不是一回事 |
| Claude Managed Agents | 每个 Agent 有独立 session thread；共享基础设施不等于共享上下文、工具和历史 |
| DeepSeek Harness | 用 `ctx.subagents` 统一多种 provider，并提供 persona、工具过滤和委派深度等边界 |
| A2A v1.0 | 用 Message 交流，用 Artifact 正式交付；协议负责互通，业务负责验收 |

不同 Harness 使用不同名字表达协作：manager / worker、coordinator / specialist、agent / subagent。**接口名称会变化，但协作系统需要回答的问题并没有变化**。

## 七、小结

协作扩大了 Agent 可以同时处理的工作范围，也把原来集中在单一上下文里的决定拆散到了多个执行者手中。系统由此获得并行、隔离和专业化，也开始承担通信、等待、聚合、版本和责任成本。

> **多 Agent 架构真正需要设计的是 Agent 之间的边界**。

协作模式组的任务，是让工作**分得出去、收得回来、争得明白、接得安全**。采用多 Agent 以前，先看边界是否清楚。采用多 Agent 之后，要注意清晰的分工和明确的责任。

> 设计好一个 Agent 系统，实现"意图随消息，真值随引用，结果随工件，责任随验收"之后；也应该思考，在组织和团队的管理过程中，是否也应该像设计多 Agent 协作系统一样，有清晰的目标设定和高效的沟通机制，为每个团队、每一个人制定明确的责任和交付工件的结果形状。

## 八、思考题

1. 你当前设计里的多个 Agent，各自承担哪一块**不可替代**的责任？
   - 删除其中一个 Agent，最终交付会明确少掉什么？
   - 如果答案是"好像也不会少什么"，它可能只是一次昂贵的重复调用。
2. 多位 Agent 得出不同结论时：
   - 谁有权修改最终工件？
   - 谁有权宣布通过？
   - 谁负责保留被否决版本的证据？
