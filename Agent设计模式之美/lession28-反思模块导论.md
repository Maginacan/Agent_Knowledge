# 26｜反思模块导论：让 Agent 站到自己的结果之外

> **核心命题**：反思，是把已经发生的任务产出与**可复核基准**进行比较，识别偏差，在授权范围内改变后续系统行为，再用**独立的结果信号验收**这次改变的反馈机制。
>
> **反思要接入新证据，还要检查这份证据是否真的解释了结果变化**。从"再想一次"走到"改变一个条件，再观察结果"，反思才开始接近可验证的工程机制。

---

## 一、行动模块留下的问题

行动模块负责把模型的判断安全地做出来：工具要先取得准入，多步任务要受计划约束，中间工件要经过验收，高风险动作还要穿过前置与后置守卫。**但动作完成以后，仍然可能留下另一类问题**。

### 1.1 月报与账本不一致

> 账本里有 798 张工资单处于 PAID，E0007 和 E0012 已经冲正，状态是 `REVERSED`；**财务月报却写着 `month=2026-06 paid=800`**。业务终态已经形成，但月报没有如实反映，**行动过程本身也没有发现这道差异**。

### 1.2 补偿性错误

> 更隐蔽的情况是，发薪 Agent 算出的总额、人数和五险一金合计全部正确，**但其中一人多发一元，另一人少发一元，两笔错误刚好抵消**。只看汇总数字，系统会认为一切正常；**只有把每名员工的工资单与权威明细逐条比对，才能发现问题**。至于错误来自舍入、结转、录入还是科目映射，还要继续调查。

### 1.3 反思模块要解决的问题

> 一个能把总账对平、还能自圆其说的系统，**怎样知道自己其实错了**？这就是反思模块要解决的问题。
>
> - 系统说任务成功，**业务状态真的成功了吗**？
> - 发现偏差以后，**应该改当前报告、调整下个月的技能，还是直接修改代码**？
> - 连续修了三轮，**究竟是在接近目标，还是只围着最后一个报错打转**？

## 二、会回头看 ≠ 会反思

> **模型可以重读答案、写一段复盘，或者重新生成，但工程系统真正需要的是一条能够连接结果、证据、改变与停止的反馈路径**。

| 维度 | 推理 | 反思 |
|------|------|------|
| 关心什么 | **决定接下来做什么** | **把已经发生的结果重新送回系统，约束后续行为** |
| 区别不在发生时间 | — | 而在于**有没有新的结果信号进入系统** |
| 如果输入、工具和事实源都没有变化 | 继续推理 | 只是**重试、重采样或继续推理，还不是这里所说的反思** |

## 三、六个问题构成的反思契约

| 问题 | 要固定的内容 |
|------|------------|
| **反思谁** | 被审对象及其**版本** |
| **回到哪里** | 原始目标与成功标准 |
| **拿什么对照** | 检测偏差用的数据库、规则、字段结构、测试、指标或人工判断**及其版本** |
| **允许改变什么** | 当前产出、能力路由、经验上下文或系统状态 |
| **改完怎样验收** | 用哪套独立检查判断这次改动真的成功，看的是哪些结果信号 |
| **何时停止、回到哪** | 通过 / 预算耗尽 / 无进展 / 风险升高 / 人工接管，以及**停止后回到哪个基线、怎样回、失败交给谁** |

### 3.1 ReflectionContract

```python
@dataclass(frozen=True)
class ReflectionContract:
    contract_version: str
    subject_ref: str
    goal_ref: str
    evidence_refs: tuple[str, ...]      # 检测偏差的证据
    allowed_changes: frozenset[str]
    acceptance_ref: str                 # 改完怎样重新验收
    stop_conditions: tuple[str, ...]
    recovery_ref: str | None            # 停止或失败后回到哪、怎样回、交给谁
```

### 3.2 ValidatorPolicy（治理契约）

> 还有一层契约，**不属于这次反思本身，而属于治理**。治理契约判断用来验收的这面镜子凭什么可信，具体包括**数据库快照，测试和模型评分器如何维护、怎样校准、回归测试是什么、什么时候过期**：

```python
# 运行时契约回答"这次改得对不对"
# 治理契约回答"判断对错的这套东西本身还可不可信"
@dataclass(frozen=True)
class ValidatorPolicy:
    validator_ref: str
    owner: str
    calibration: str
    regression_suite_ref: str
    expires_at: datetime | None
```

> **反思能力越强，拥有的权限越多，而权限每深入一层，外部信号、验收、停止线和回滚的责任都要跟着加厚**。

### 3.3 测量和治理的三个要点

1. **反馈的质量取决于测量**。测量如果拿不到真实业务状态，只能评价文本是否自洽，基本没啥用，因为大模型文本上基本都自洽
2. **发现偏差与修改系统是两种权限**。测试过程不应该顺手修改生产代码。批评者提出问题，修复和放行要经过独立策略
3. **反馈回路必须能够停止**。就像 CI 会在失败时阻断合并，**自动修复器也需要轮次的预算、无进展检测机制以及回滚的出口**

> 因此，**反思仍然是工程，不是仅仅通过几句提示词，让 LLM 把判断、解释和修订变成了自然语言就完事儿了**。比如找到另外一个模型说"你检查检查，反思反思"，这样做的确简单，反馈成本很低，但**这样的设计聊胜于无，抓不到关键问题，我认为意义不大**。

## 五、叙事态 vs 机械态

> **梁博老师**在他的执行型 Agent 的企业落地蓝皮书中，也反复强调**模型的叙述状态和机械的控制状态要分开管理**。

| 状态类型 | 职责 | 例子 |
|---------|------|------|
| **叙事态** | 保存用户目标、任务进展、里程碑和自然语言摘要，让模型**知道自己正在做什么** | 月报"全部支付成功" |
| **机械态** | 保存业务对象 ID、版本、状态、参数绑定、外部回执和数据库事实，让系统**知道实际发生了什么** | 工资单状态、银行回执、冲正记录 |

> **叙事态缺失，Agent 容易在长任务里失去目标。机械态缺失，系统就只能相信模型对执行结果的讲述**。二者配合起来，才能完成反思。

### 5.1 反思读的是机械态，产出的是变更提案

> 执行型 Agent 的反思，**如果只让叙事态评价叙事态**。月报说"全部支付成功"，再让同一段上下文检查"这句话是否合理"，很容易得到一个内部自洽的通过结论。**而加入机械平面中的工资单状态、银行回执和冲正记录才是完整证据链**。

> 除了把两种状态的数据结构分开之外，**还要有权限边界**：
> - 模型可以**读取机械态、解释机械态、提出对机械态的变更**
> - **一段叙事文本不能直接覆盖机械态**
> - **机械态只能通过受约束的业务接口改变**
>
> 否则"月报说全发了"这句话，就可能被当成"账本已经全发了"写回系统。

### 5.2 反思在企业系统里更重

> 这也解释了为什么反思在企业系统里常常比内容生成场景更重。文案写得不满意，用户可以重新生成。**业务状态已经改变以后，错误会进入账本、审批、通知和下游流程**。
>
> 反思更应该面对的是**已经发生变化的世界**（当然你写个文章、PPT 时，多反思一两次有益无害）。

## 六、反思的工程定义

> **反思，是把已经发生的任务产出与可复核基准进行比较，识别偏差，在授权范围内改变后续系统行为，再用独立的结果信号验收这次改变的反馈机制**。

### 6.1 反思闭环（真正的 Loop Engineering）

```text
已发生的结果
  → 版本化证据
  → 偏差识别
  → 归因假设（可选）
  → 归因验证或干预证据（可选）
     # 没有外部信号，回路容易变成自我确认
  → 授权范围内的改变
     # 改变权限，批评可能顺手修改不该触碰的对象
  → 独立重新验收
     # 有独立验收，系统只知道"改过"，不知道"改对"
  → 通过、继续、回滚或交人
     # 没有停止和恢复，反思会演化成长程任务里的负担
```

### 6.2 "发现不一致" ≠ "知道为什么不一致"

> 月报对账能证明 800 和 798 对不上是**偏差识别**；至于原因是旧快照、状态映射错误、数据延迟，还是汇总逻辑漏了冲正，对账本身证明不了。
>
> **所以归因是可选的一步**：发现偏差，系统已经可以拒绝放行，**要注意 LLM 会不会为了显得聪明去编一个根因**。
>
> **除非做到受控回放和针对性干预**（参考 REFLECT 论文），让结果能翻转，才把偏差升级；**普通对账过程中发现了偏差的时候，其实反思过程就可以结束了**。

## 七、反思模块中的四个模式

反思模块包含四个模式。**它们不按模型调用次数排序，也不表示自动化程度逐步提高**。区分它们的根本依据是：**结果反馈最终改变了哪一种系统对象**。

> 链式、路由、层级、循环是它们各自的实现拓扑，**不是它们成立的理由**。

> 这张图要分三层看：
> - **改变对象决定模式的性质**
> - **执行拓扑决定模式怎样实现**
> - **治理风险取决于改变持续多久、对业务状态有多直接**

### 7.1 四模式对照表

| 对应讲数 | 模式 | 改变对象 | 执行拓扑 | 持续范围 | 改变直接性 | 核心风险 |
|---------|------|---------|---------|---------|----------|---------|
| **27** | [[lession29-生成评审\|生成评审]] | **当前产出** | 链式 | 单次版本 | 低（只裁决版本）| 错误放行 |
| **28** | [[lession30-技能包\|技能包]] | **可复用能力的准入** | 路由 | 跨任务 | 中（控制路由与能力）| 未验证能力获得流量 |
| **29** | [[lession31-经验回放\|经验回放]] | **后续任务的经验上下文** | 层级 | 跨任务 | 低（只作建议）| 错误经验被长期放大 |
| **30** | [[lession32-自愈循环\|自愈循环]] | **代码、配置与运行状态** | 循环 | 系统级 | **高**（直接改系统）| 破坏状态、循环失控 |

> **持续范围和改变直接性并不总能排成一条直线**。一条经验可能只作为背景提示，模型可以不采用；一个进入正式路由的技能，却可能直接调用付款工具。**因此，四个模式不应该被简单理解成从浅到深的一条阶梯**。

### 7.2 各模式简介

#### 生成评审

> 评审者提出有证据的问题，策略闸决定当前版本能否通过。**根据评审产生的修订稿，是一个新的版本，还没有接受审查，不能继承原稿的裁决**。

#### 技能包

> 一次成功轨迹只能成为**候选技能**。候选先处于 `TRIAL`，通过外部验证以后，才能进入正式路由。**技能进入路由后，真实复用结果还要继续写回**。表现下降、政策变化或凭证过期时，**旧资格必须能够被撤销**。

#### 经验回放

> 它最难的地方是**信用分配**。一次任务同时注入五条经验，最后成功了，不能把五条经验全部记成有效。**系统需要记录哪些经验被使用、后续结果怎样，再通过真实战绩把教训和迷信分开**。

#### 自愈循环

> 测试红灯触发诊断和补丁，补丁经过审查后原子应用，再重新验证。**只要问题仍然存在，并且没有触发停止线，循环就可以继续**。如果修复失败，系统必须恢复基线，并把原始目标、测试证据和尝试过的补丁交给人工。
>
> **它的目标不是让最后一个测试勉强转绿，而是恢复原始目标约束下的系统正确性**。

## 八、反思与评估、记忆的区别

### 8.1 评估 vs 反思

| 评估 | 反思 |
|------|------|
| 回答"**这次做得怎么样**" | 还要回答"**这个判断准备改变什么，改变以后怎样重新验证**" |
| 可以停在分数、标签或裁决 | 是一条**完整的反馈回路** |
| — | **评估是反思的信号入口** |

> 在 *Designing AI Agents* 一书中，作者把**评估纳入了反思模块**。

### 8.2 记忆 vs 反思

| 记忆 | 反思 |
| ------------- | ------ |
| 负责把过去留下来 | 还要判断**这次失败说明了什么、是否值得影响下一次任务、以及复用以后有没有真正改善结果** |
| 失败日记可以完整保存 E0012 的冲正轨迹 | "保存了" ≠ "已经学会了" |
| 尚未证明的教训 | 只能作为**带来源的背景信息** |
| 经过多次验证、能够稳定检查的经验 | 才可能升级成**规则、护栏或技能** |

### 8.3 模式之间边界

| 边界 | 含义 |
|------|------|
| **生成评审 vs 自愈循环** | 生成评审结束于一次版本裁决；自愈循环结束于外部红灯转绿，或者停止策略接管 |
| **技能包 vs 经验回放** | 技能包保存的是可以执行的能力；经验回放保存的是可能有帮助、但尚未完全固化的背景教训 |

> **这些边界会直接决定数据结构**：
> - **生成评审**要保存被审版本和未复审的新稿
> - **自愈循环**要保存失败签名、补丁指纹和回滚栈
> - **技能包**要保存版本、生命周期和路由记录
> - **经验回放**要保存原始轨迹指针、注入记录和复用效果

## 九、谁来检查反思本身

> **反思需要外部信号，但"外部"不等于"绝对正确"**。
>
> 数据库里的数据可能已经过期，业务规则可能漏掉特殊情况，测试用例也可能只覆盖正常流程。模型评分器可能偏爱自己熟悉的表达方式，人工审核同样会疲劳，也会出现意见分歧。**所以，不能因为一份证据来自模型外部，就直接把它当成最终真相**。

### 9.1 三类检查方式

| 检查方式 | 适合检查 | 主要风险 |
|---------|---------|---------|
| **代码与环境检查** | 字段、状态、测试结果、工具参数和业务不变量 | 可能过于僵硬，无法处理合法变化 |
| **模型评分器** | 语义质量、完整性和开放式内容 | 非确定性、自我偏好，需要校准 |
| **人工审核** | 专业责任、模糊边界和高风险决定 | 成本高、速度慢，判断可能不一致 |

> 它们各有长处，也各有盲区，**不能只依赖其中一种**。

### 9.2 三样必须分开检查的东西

> **检查对象也不能只有 Agent 最后说出的那句话，至少要分开检查三样东西**：
> 1. **最终输出**
> 2. **完整执行轨迹**
> 3. **环境中的真实终态**

例如，Agent 最后说"任务已经完成"，执行记录却可能显示它绕过了审批，数据库中甚至没有留下成功记录。**如果只检查最后一句话，就会同时漏掉过程违规和结果失败**。

### 9.3 ValidatorPolicy 要解决的问题

```text
- 谁负责维护这些检查器
- 多久校准一次
- 测试集是否仍然有效
- 业务规则变化以后有没有及时更新
- 什么时候需要人工抽检
```

> **运行时验收回答的是"这一次修改到底改对了没有？"；验证器治理回答的是"用来判断对错的这把尺子，现在还准不准？"**
>
> **反思系统不但要检查 Agent，也要定期检查自己的评分器、业务规则和测试**。否则，Agent 可能越来越擅长通过旧指标，却离真实业务目标越来越远。

## 十、长程 Agent 最怕反思也跟着走偏

> **短任务做错了，影响通常只停留在这一份答案里。长程 Agent 不一样**。它会一边执行，一边修改外部环境，再把修改后的结果读回来，作为下一轮判断的依据。
>
> 这意味着，**一个最初很小的错误，如果没有及时发现，可能会被后面的步骤当成真实事实继续使用**。Agent 先根据错误信息做出判断，又把判断结果写回系统，下一轮再以这个结果为起点。**循环几次以后，最初的猜测就可能越来越像一件已经确认的事实**。

### 10.1 反思设计不好的四种后果

- **围错误打补丁**：Agent 一直围着最近出现的一个报错打补丁。眼前的测试通过了，它就认为问题解决了，却**忘记了整个任务原本要达到什么目标**
- **偶然成功固化为技能**：把一次偶然成功的方法整理成技能，**以后反复调用**
- **错误归因被稳定复用**：任务碰巧成功，就把五条经验**全部当成有效结论**保存下来

### 10.2 长程 Agent 必须保留的三条线

| 线 | 含义 |
|----|------|
| **目标线** | 每次修改以后，都要回头检查，它是否仍然服务于最初的任务目标和成功标准，**而不是只解决了眼前的一个报错** |
| **证据线** | 每个判断都要能够追溯到具体的数据库记录、测试结果、业务规则或人工意见，**而且要知道使用的是哪个版本** |
| **恢复线** | 如果修改没有成功，系统要知道应该回到哪个干净状态；如果已经无法安全恢复，也要及时停止，**把现状和证据交给人工处理** |

> 前面的行动模块已经留下了目标契约、动作记录和检查点。**反思模块不是重新编一套故事，而是接过这些真实记录**，判断当前偏差是否值得修改、允许修改到什么程度，以及修改失败后怎样退回来。
>
> **行动负责让任务向前走，反思负责在走偏以后把它拉回来**。两者连在一起，长程 Agent 才不会因为解决了眼前的小问题，反而忘记了自己最初为什么出发。

## 十一、薪酬例子反思流程

### 11.1 实验设定

```text
月报说 800 笔工资已经支付，没有冲正
账本中实际只有 798 笔处于 PAID
另外两笔已经变成 REVERSED
```

**这个实验只隔离一个变量：检查器有没有看到月报之外的账本事实**。

### 11.2 启动命令

```bash
cd agent-design-patterns
uv sync --extra ui
uv run --extra ui python reflection/payroll-lab/web_app.py
# 浏览器打开 http://127.0.0.1:8766
# 选择"月末场景"
```

> 行动模块中的实验彼此隔离，**每次运行结束都会恢复自己的基线**。为了让反思模块的五讲从同一个状态开始，`bench.py` 会确定性重建一个月末场景：798 笔支付成功，2 笔已经冲正。

### 11.3 Agent 月报

```text
MONTHLY-REPORT month=2026-06
paid=800 reversed=0 exceptions=none conclusion=all-clear
```

> 只看这份文字，它没有明显问题。**格式完整，几个数字互相一致，最后的 all-clear 也能从 paid=800、reversed=0 推出来**。问题在于账本里发生的事情和它写的不一样。

### 11.4 第一轮：内省批评者（无账本访问）

```text
== run 1: introspective critic (strict=False) ==
   attempt 1 (first pass): APPROVED, score 96/100
      - format complete
      - numbers internally consistent
      - conclusion follows from stated numbers
   attempt 2 (asked to double-check, same critic): APPROVED, score 96/100
```

```python
def self_grade(report, strict=False):
    """Introspective critic: the same mock model re-reads its own report.
    It can check format and internal consistency. It has no ledger access,
    so it cannot check truth. Strict mode lowers the score, not the blind spot."""
    notes = ["format complete", "numbers internally consistent",
             "conclusion follows from stated numbers"]
    if strict:
        notes.append("tone could be more cautious")
        return 88, notes
    return 96, notes
```

### 11.5 第二轮：账本对账

```text
== run 2: reconciliation against the ledger (two SQL queries) ==
   REJECTED: report says paid=800, ledger counts 798
   REJECTED: report says reversed=0, ledger has 2 REVERSED rows (E0007, E0012)
```

```python
paid_db = con.execute(
    "SELECT COUNT(*) FROM payroll WHERE month=? AND status='PAID'",
    (MONTH,)
).fetchone()[0]
reversed_rows = con.execute(
    "SELECT emp_id FROM payroll WHERE month=? AND status='REVERSED'",
    (MONTH,)
).fetchall()
```

### 11.6 退回并修改后的月报

```text
MONTHLY-REPORT month=2026-06
paid=798 reversed=2 exceptions=E0007,E0012
conclusion=exceptions-pending
```

> **真正改变结论的，不是批评者说话更严厉，而是检查过程接入了月报之外的事实**。

### 11.7 关键概念区分

| 概念 | 检查什么 |
|------|---------|
| **自洽** | 月报与**它自己**的关系 |
| **真实** | 月报与**账本**的关系 |

> **手里没有账本的批评者，只能检查前者**。

### 11.8 变量对比

| 检查者 | 有没有账本证据 | 结果 |
|--------|--------------|------|
| 同一批评器 | 否 | 只能查格式和内部一致，96 分放行 |
| 同一批评器 | **是** | 指出月报与账本不符，**退回** |
| 更严格的提示词 | 否 | 分数降到 88，**事实盲区不变** |
| **确定性 SQL 验收** | **是** | **直接拒绝**，给出 798 与两笔冲正 |

> **改变结论的不是更强的模型，也不是把提示词写得更严格，而是让检查过程真正拿到了业务事实**。

## 十二、6 个反思契约的答案

回到前面的反思契约，这个例子中的六个问题都有明确答案：

| 反思契约 | 薪酬例子答案 |
|---------|------------|
| **反思谁** | 检查的是那份声称 `all-clear` 的月报，**而且必须固定它的具体版本** |
| **回到哪里** | 回到月报最初的目标——**如实反映 2026 年 6 月账本的最终状态** |
| **拿什么对照** | 对照 payroll 表中的两类数据：`PAID` 状态的数量；`REVERSED` 状态的工资单及员工编号 |
| **允许改变什么** | 这一轮**只允许修改月报文本**，不允许反思器直接修改工资账本 |
| **改完怎样验收** | 修改后的月报还要重新运行同样的对账查询。**只有月报数字和账本状态重新一致，才能通过** |
| **何时停止、失败后怎么办** | 对账通过就停止。**如果账本状态无法解释，或者差异无法在授权范围内处理，就停止自动修改，把问题交给财务人员** |

> 工作台的数据库页面中还保留着一条更早的记录。在 E0012 的备注字段里，保存着 [[lession21-并行探索\|第 19 讲]] 留下的异议：
>
> ```text
> DISSENT-ON-RECORD: old vs new policy disagreed (9600 vs 8200), lecture 19
> ```
>
> **这条记录说明，其实反思照见的正是前面模块已经留下的业务痕迹**。账本、冲正状态和异议备注原本就在系统里，反思回路要做的是把这些事实接回判断，让月报接受真实业务状态的检查，而不是临时编一份"外部信号"。

## 十四、反思指标

> 判断反思系统好不好，**不能只看它"反思了多少轮"**。让 Agent 连续评论十遍，未必比一次准确的账本查询更有价值。真正值得观察的是它是否获得了正确证据，有没有阻止错误版本通过，有没有越权修改，以及失败以后能不能安全退回来。

| 指标 | 含义 |
|------|------|
| **结果信号覆盖率** | 有多少关键结论真正经过数据库、测试、业务规则或人工审核 |
| **轨迹与终态分歧率** | Agent 在对话中声称"已经完成"，但业务系统中实际没有完成的任务占多少 |
| **错误放行率** | 系统已经发现严重问题以后，错误版本仍然被批准的比例 |
| **越权改变率** | 反思器是否修改了契约不允许它触碰的对象 |
| **无进展循环率** | 同一种错误配上同一种补丁，连续重复出现的比例 |
| **基线恢复率** | 自动修复失败以后，系统完整回到了修改前的干净状态的比例 |
| **经验与技能的复用收益** | 注入经验或把技能放进路由以后，真实任务结果是否比原来更好 |

> **这些指标不能脱离业务风险单独看**。薪酬放行、客服文案和代码格式化的错误代价完全不同。它们不应该共用同一条看似整齐的健康线，而要根据风险、可逆性和人工介入能力设置不同标准。

## 十五、思考题

1. 你的 Agent 第二次检查时，**究竟获得了什么新信息**？如果输入、工具和事实源都没有变化，为什么第二次结论会更可靠？
2. 找一条真实的反思记录。它最后改变的是**当前输出、能力路由、经验上下文，还是代码与业务状态**？这项改变是否在原来的授权范围内？
3. 选择一个你最信任的外部信号，例如数据库、测试或人工审核。**它由谁维护，多久更新一次**？如果这套检查本身出错，系统怎样发现？
4. 当自动修复没有让测试转绿时，系统**能不能证明自己已经回到修改前的干净状态**？交给人工时，能否同时提供原始目标、尝试过的补丁和停止原因？
