## 一句话核心

> **语义压缩（Semantic Compaction）= 在长任务里持续维护 Agent 的工作记忆，确保它还记得自己为什么走到这一步。**

## 一、为什么需要语义压缩

### 1.1 上一讲的尾巴与本讲的开头

上一讲 [[lession9-上下文分诊]] 处理了**选什么进 Context**：候选信息太多时，先决定什么进、什么留外、什么只挂 handle。但信息进来只是个良好开端——

> Agent 只要跑得足够久，上下文一定会膨胀。对话历史、tool 返回、错误日志、代码 diff、测试结果，一轮一轮堆起来。到了某个时刻，系统必须压缩历史，否则不是撞上 context limit，就是让模型淹在旧信息里。

### 1.2 压缩的两个层次问题

| 层次 | 问题 |
|------|------|
| 表层 | 压缩当然能省 token |
| **深层** | 压缩之后 Agent 还记不记得**为什么走到这一步** |

> **关键洞见**：坏的压缩会把关键证据压没；更坏的压缩会让 Agent 忘记哪些方案已经失败，然后在同一个坑里反复试错。

### 1.3 反例：数据库故障排查 Agent

刚看到一条关键错误：

```
ConnectionPoolExhausted: pool_size=20, queue_depth=347
  at /app/db/pool.py:142
  ... (14 lines stack trace)
  Cause: timeout in _acquire_connection
```

**真正有价值的细节**：`pool_size=20`、`queue_depth=347`、`_acquire_connection timeout` —— 这些暗示问题不是简单把连接池调大，而是**连接没有被及时释放**。

如果 compaction 把这段压成：

> "a database error occurred"

Agent 就失去了判断力。它后面可能继续调 pool size、加 retry、改 timeout —— 看起来还在努力，实际上已经忘了最重要的线索。

## 二、如何理解语义压缩模式

### 2.1 在双轴图谱的位置

**认知功能**：感知（压缩之后留下来的内容，决定 Agent 下一轮还能看见什么）。

**执行拓扑**：链（压缩通常不是一步完成，而是一层一层往下压）。

### 2.2 三层压缩链

| 层 | 动作 | 处理对象 |
|----|------|----------|
| **L1 工具结果清理** | 替换冗长 tool output 为占位符 | 日志全文、API 返回、查询结果 |
| **L2 对话/任务摘要** | 合并旧对话成任务状态 | 用户意图、已做改动、已做决策、下一步 |
| **L3 渐进式 summarize** | 极限压缩（仅在 context 压力很大时触发）| 历史全文 → 摘要 |

> 每一层都接住上一层的输出，**越往后越短，也越容易丢细节**。

### 2.3 特德·姜的"模糊图像"类比

> 在大语言模型诞生初期，《降临》作者**特德·姜**写过一篇著名的文章，《ChatGPT 是网上所有文本的模糊图像》。这篇文章充满哲思。其中有个**模糊图像**的类比也非常适合此处。
>
> 你可以想象暗房里不断翻拍照片：第一次翻拍，主体还在；第二次翻拍，边缘开始糊；第三次再翻拍，很多细节就永久丢了。
>
> **多层压缩也一样。压缩次数越多，语义漂移的风险越大。**

**最稳的策略**：少压、分层压、保留证据、保留回退路径。

### 2.4 模式定义

> **语义压缩模式** = 在尽可能保留关键语义信息的前提下，决定哪些内容可以丢弃、哪些内容必须保留，以及将保留的信息压缩到何种粒度。
>
> 它要确保压缩之后，Agent 还能记得自己为什么走到这一步。

## 三、什么时候该用语义压缩

只要 Agent 进入**长任务**，就应该考虑：

| 触发条件 | 阈值建议 |
|----------|----------|
| 会话轮次 | 超过 20-30 轮 |
| context 占用 | 超过 60%-70%（高风险任务可提前到 50-55%）|
| tool 结果堆积 | 日志、测试输出、代码 diff 明显膨胀 |
| 行为异常 | Agent 开始重复问、重复查、重复试 |

> **两种错误**：不压 → Agent 撞上 context limit；乱压 → Agent 忘掉关键证据。真正好的压缩，是让 Agent 在长 session 里继续保持清醒。

### 3.1 一类内容不能被普通摘要吞掉：错误信息

- 错误堆栈
- 失败测试
- 异常日志
- 关键数字
- 文件路径、行号

这些都是 **Agent 的反馈回路**，不能被压成一句模糊结论。

| 错误长度 | 处理方式 |
|----------|----------|
| 短错误栈 | 原文保留 |
| 长错误栈 | 保留异常类型、关键数字、文件路径、行号、首尾几段、原始日志 handle |

> **已经失败过的方案**，也要进入工作记忆锚点（**anchor**），告诉 Agent "这条路不要再走"。

## 四、工程现场切片

### 切片对比总览

| 切片 | 来源 | 核心机制 | 关键启发 |
|------|------|----------|----------|
| 切片一 | Claude Code | 自动压缩 + 早触发 | 短任务晚压、长任务早压 |
| 切片二 | Factory | 锚定式迭代摘要 | 维护持续演化的 anchor |
| 切片三 | OpenHands | 可配置压缩器 | 按内容类型分治 |

### 切片一：Claude Code 的自动压缩

Claude Code 内置 **auto-compaction**，在上下文接近上限时自动压缩旧内容，避免 session 撞上 context limit。

**优点**：开箱即用，用户不需要手动整理历史，Agent 可以继续往下跑。

**问题**：压缩不能只看"窗口有没有满"——长 context 的风险不只是装不下，还有**推理质量下降**。

> 等到 context 已经接近满了再压，可能意味着 Agent 在最后一段已经处于**注意力变差、判断变弱**的状态。再把这段低质量历史压进摘要，就会污染下一轮推理。

**重度用户的工程实践**：在 **60%-70%** 左右主动压缩。

> 看似浪费窗口，但背后的逻辑是：**不要等 Agent 变笨之后再压，而是在它还清醒的时候整理历史**。

**工程启发**：

> **短任务可以晚压，长会话、高风险任务应该早压**。

### 切片二：Factory 的锚定式迭代摘要

Factory（也是一家 AI Coding 公司）也提出重点不是"要不要压"，而是"**压完之后历史怎么持续演化**"。

| 方案 | 演化路径 | 风险 |
|------|----------|------|
| 普通摘要 | 摘要 → 摘要的摘要 → 摘要的摘要的摘要 | 越来越模糊（复印件反复复印）|
| **Factory anchor** | 摘要0 → 摘要1 → 摘要2（**anchor 仍然清晰**）| 持续稳定 |

**anchor 至少要保住五类信息**：

| 字段 | 含义 | 工程意义 |
|------|------|----------|
| **Intent** | 用户要什么 | 不偏离目标 |
| **Changes made** | 已经改了什么、调用了什么 | 不重复劳动 |
| **Decisions taken** | 已经做了哪些判断 | 不反复摇摆 |
| **Excluded approaches** | **已经排除的方案** | **不再走老路** |
| **Next steps** | 下一步做什么 | 不卡壳 |

> **黄佳建议再加一个更工程化的字段：`excluded_approaches`（已排除的方案）**。
>
> 很多 Agent 在长 session 里反复试错，不是因为不会推理，而是因为**忘了哪些路已经走不通**。

回到数据库故障排查的开头例子：

> Agent 一直加 pool size、加 retry、调 timeout，本质上就是缺少"**不要再试这些方案**"的记忆槽位。

**所以生产系统中 Agent 的 Anchor 应该能回答五个问题**：

1. 用户要什么？
2. 我做过什么？
3. 我决定了什么？
4. 我**排除了**什么？
5. 下一步做什么？

> 这比每次粗暴重写摘要稳定得多。

### 切片三：OpenHands 的可配置压缩器

**OpenHands 的设计哲学**：不同 Agent 的历史，不应该用同一种方式压缩。

它把压缩打包成可配置的模块（OpenHands 中被称作 **condenser**），让开发者按任务选择策略：

| 策略 | 适用场景 |
|------|----------|
| 不压 | 短任务 |
| 只保留最近事件 | 中等任务 |
| LLM 摘要 | 标准长任务 |
| **ObservationMasking**（观察结果遮蔽）| **日志/SQL/API 输出密集型** |
| 渐进遗忘 | 资源极度紧张 |

**最值得注意的是 ObservationMasking**：

Agent 历史里有两类信息：

| 类型 | 含义 | 例子 |
|------|------|------|
| **Action** | Agent 做过什么 | 读文件、调接口、执行命令 |
| **Observation** | 外部世界返回了什么 | 日志全文、API 响应、测试输出 |

> 很多工程场景里，Agent 后续**不一定需要保留所有 Observation 原文**，但**必须记住自己做过哪些 Action**。
>
> ObservationMasking 的做法就是**把早期 Observation 替换成占位符，但保留 Action**。

> 相当于告诉 Agent：**你不需要记住每一屏输出，但必须记住自己走过哪些路**。

**工程判断**：

> 如果你的 Agent token 主要花在日志、SQL 查询结果、API 响应、测试输出上，而后续推理更依赖"做过哪些动作、得出哪些结论"，那 **ObservationMasking 往往比通用 LLM summarization 更稳**，既省 token，也减少语义漂移。

### 切片归纳：三条工程原则

| 原则 | 来源 | 含义 |
|------|------|------|
| **自动** | Claude Code | 必须自动化，否则长 session 迟早撞墙 |
| **演化** | Factory | 不要每次重写历史，而要维护持续演化的 anchor |
| **分治** | OpenHands | 不能只有一种算法，要按 Action/Observation/Error/Decision 不同性质分层处理 |

## 五、8 框架横切：每家怎么做 Compaction

> 把几家主流 harness 放在一起看，会发现 **Compaction 没有标准答案，只有不同取舍**。

| 关键判断 | 含义 |
|----------|------|
| Compaction 是取舍 | Claude Code 简单，OpenHands 灵活，Aider 透明，OpenCode 解耦 —— 没有一个方案在所有场景都最优 |
| 不做 Compaction 也是一种选择 | 但只适合短任务；任务一长，Agent 容易忘记做过什么、排除过什么、为什么走到当前这一步 |
| **Compaction 和 Memory 要分清** | Compaction 管当前 session 怎么续命；Memory 管跨 session 的经验怎么沉淀。前者解决窗口压力，后者解决长期记忆 |

**生产系统的正确问法**：

> 不要问"哪家方案最好"，而要问：
>
> 1. 我的 Agent 会话有多长？
> 2. 工具输出有多大？
> 3. 错误密度有多高？
> 4. 翻车成本有多大？

| 场景特征 | 推荐压缩策略 |
|----------|--------------|
| 短问答 | 轻量处理 |
| 长调试 | 必须有 anchor |
| 大量日志 | 适合 ObservationMasking |
| 跨会话复用经验 | 应该进入 Memory 设计 |

## 六、工业级实现：可观测 Compaction 的最小骨架

> **Semantic Compaction 不能只是一个 `summarize_history()` 函数。**
>
> 生产里的 compactor 至少要做四件事：
>
> 1. **什么时候压**
> 2. **哪些信息能压**
> 3. **哪些信息必须保护**
> 4. **压缩过程能不能被追踪**

### 6.1 三个核心对象

#### 对象一：Turn（一轮对话/工具调用/工具返回）

```python
from dataclasses import dataclass

@dataclass
class Turn:
    role: str
    content: str
    tokens: int
    is_error: bool = False  # 关键：错误堆栈、失败测试、异常日志不能按普通文本压缩
```

**`is_error` 是最关键字段**：

> 错误堆栈、失败测试、异常日志**不能按普通文本压缩**，因为它们是 Agent 的反馈回路。

#### 对象二：CompactionAnchor（压缩后的工作记忆）

```python
from dataclasses import dataclass, field

@dataclass
class CompactionAnchor:
    intent: str = ""
    changes_made: list[str] = field(default_factory=list)
    decisions_taken: list[str] = field(default_factory=list)
    excluded_approaches: list[str] = field(default_factory=list)
    next_steps: list[str] = field(default_factory=list)
```

**它应该稳定回答五个问题**（其中 `excluded_approaches` 最重要）：

> 很多长会话 Agent 反复试错，不是因为不会推理，而是**忘了哪些方案已经失败**。

#### 对象三：CompactionEvent（每次压缩的可观测记录）

```python
@dataclass
class CompactionEvent:
    level: int
    tokens_before: int
    tokens_after: int
    error_traces_preserved: int  # 必须留下事件记录，否则 Agent 后面变蠢，你不知道是哪一次压丢的
```

> 没有这个对象，**压缩就变成黑盒**，Agent 后面变蠢了，你也不知道它是在哪一次压缩里丢了信息。

### 6.2 三层压缩的实现策略

| Level | 触发条件 | 动作 |
|-------|----------|------|
| **L1 工具结果清理** | 长 tool output 出现 | 日志/API/查询结果，若非错误信息，先替换成占位符 |
| **L2 合并进 Anchor** | L1 不够时 | 把旧历史抽取成 intent/changes/decisions/excluded/next，增量合并到 anchor |
| **L3 极限压缩** | 不得不用时 | **也可作为退场信号**——多次触发 L3 意味着该交接、开新 session 或转人工 |

> 完整的范例实现代码请参考 Repo 语义压缩模式实现部分。代码是如何实现上面的三层压缩的，大家可以在 AI 辅助之下进行分析，也可以和 AI 切磋新思路。

## 七、业务场景：长会话客服 Agent 的压缩实战

### 7.1 客服场景特征

客服 Agent 处理复杂工单时，通常会：

| 维度 | 典型范围 |
|------|----------|
| 时长 | 2-4 小时 |
| 对话轮数 | 50-150 轮 |
| 中间夹杂 | 用户描述、内部工具调用、日志返回、诊断结果、升级交接 |

这样的 session 自然需要压缩。

### 7.2 业务上下文对象 SupportContext

> 客服场景里，compactor 不能只看 token，还要看工单状态：

```python
@dataclass
class SupportContext:
    ticket_id: str
    customer_id: str
    product_line: str
    severity: str              # P1 / P2 / P3
    sla_deadline_iso: str     # SLA 越近，越应该准备人工交接
```

### 7.3 三个关键业务能力

| 能力 | 含义 | 例子 |
|------|------|------|
| **按业务识别错误** | 不同场景的"错误信号"不同 | 客服：timeout、5xx、Traceback；金融：AML flag、insufficient funds；医疗：abnormal vitals、contraindication |
| **按风险调整触发阈值** | 高风险场景更早压 | 客服 P1 / 金融 / 医疗：50%-55%；内容生成 / 短代码修改：65%-70% |
| **导出交接上下文（handoff summary）** | Compaction 不只是给 Agent 续命，也是给人类交接服务 | 见下方结构 |

### 7.4 Handoff Summary 结构

```json
{
    "ticket_id": ticket_id,
    "severity": severity,
    "intent": anchor.intent,
    "changes_attempted": anchor.changes_made,
    "decisions": anchor.decisions_taken,
    "excluded_approaches": anchor.excluded_approaches,
    "next_steps": anchor.next_steps,
    "sla_deadline": sla_deadline
}
```

> 工程师看到这份摘要，应该立刻知道：**客户是谁，问题多严重，已经试过什么，哪些路不要再走，下一步该查哪里，SLA 还剩多久**。

### 7.5 三段式压缩节律（4 小时 P1 工单）

| 阶段 | 范围 | 策略 |
|------|------|------|
| **前期不压** | 前 10-20 轮 | 信息收集和假设建立，原始细节最重要 |
| **中期轻压** | 上下文接近阈值时 | 先清理冗长 tool 输出，保留错误堆栈、最近对话和关键决策 |
| **后期沉淀** | session 继续拉长 | 把旧历史合并进 anchor，让 Agent 依靠"意图、已做改动、已做决策、已排除方案、下一步"继续推理 |
| **极限压缩 / 退场** | Level 3 触发 | 准备交接 —— L3 不是"再压一次"，而是退场信号 |

## 九、Compaction 的可观测性实战

> Compaction 没有可观测性 = 黑盒。

### 9.1 三个核心指标

| 指标 | 含义 | 健康区间 | 告警条件 |
|------|------|----------|----------|
| **`level_3_trigger_rate`** | 压缩事件里的 L3 占比 | 低 | 某 session 反复进 L3 → 大量重复信息导致频繁高比例压缩 |
| **`avg_compression_ratio`** | 平均压缩比（after / before）| **0.30 - 0.50** | < 0.20 过度压缩（关键信息丢失）；> 0.60 没压够 |
| **`error_traces_preserved_per_event`** | 每次 compaction 保留的错误堆栈数 | 与真实错误对齐 | **零保留**意味着错误识别 patterns 漏了 |

> **零保留错误堆栈**意味着你的错误识别 patterns 漏了——当下一次 Agent 遇到同一个 bug，它仍然会没记忆。

### 9.2 工程落地

| 手段 | 用途 |
|------|------|
| 实时告警 + 每日报表 | Datadog / Grafana 搭看板 |
| 客户级指标波动监控 | "某天某客户的 Agent 压缩指标波动"提高警惕 |
| **anchor 演化轨迹记录** | 每次 anchor 字段变化都记录"哪些项被加进去、哪些项被覆盖、哪些项被丢" |
| 事故复盘 | 通过 anchor 演化轨迹发现"为什么 agent 在第 N 轮忘了 X" |

## 十、总结一下

### 10.1 语义压缩的核心问题

> 语义压缩的核心问题其实只有两个：
>
> 1. **什么时候该压？**
> 2. **压的时候必须保留什么？**

### 10.2 压缩的双重性质

> Agent 跑得稳不稳，**70% 看推理、30% 看记忆**，Compaction 是记忆的守护神。
>
> - **守护得好**：Agent 能在长 session 里持续清醒
> - **守护得差**：Agent 会变成失忆者

### 10.3 来自《Refactoring》的类比

> Martin Fowler 在《Refactoring》开篇时说，**refactoring 的安全感来自测试覆盖率**：因为测试在，我们才敢改代码。
>
> **语义压缩也是一样，压缩的安全感来自关键证据的保护，尤其是错误堆栈和失败记录。**

> **错误堆栈就像 Agent 的测试套件**。它记录了上一次为什么失败、失败在哪一行、关键参数是多少、哪条路已经走不通。
>
> 把错误堆栈压成一句模糊的"出现了数据库错误"，**就像重构时顺手把测试删掉**。下一次回归时，Agent 没有证据提醒自己，只能在同一个坑里再摔一次。

### 10.4 必须记住的四件事

| # | 要点 | 关键动作 |
|---|------|----------|
| 1 | **压缩不是摘要，而是工作记忆维护** | 保留用户意图、已经做过的改动、已经形成的判断、已经排除的方案、下一步计划 |
| 2 | **错误信息不能被普通摘要吞掉** | 错误堆栈、失败测试、关键数字、文件路径、行号 —— 是 Agent 的反馈回路 |
| 3 | **压缩要分层** | 先清理冗长 tool output → 再维护工作记忆锚点 → 最后才做极限压缩 |
| 4 | **压缩必须可观测** | 每一次 compaction 都应该留下事件记录 |

### 10.5 终极洞见

> 一个 Agent 能把自己的对话历史压缩得既精炼、又保留关键证据，说明它**仍然理解自己在做什么**。
>
> **坏的压缩不只是工程缺陷，也是一种认知缺陷**。它说明系统已经分不清什么是背景噪声，什么是关键证据。

> 一个学生能把整章内容总结成一段话，说明他真的理解了这一章。
>
> **你的 Agent 选择保留什么，决定它接下来能想清什么。**

>

## 十二、思考题

### 题 1：业务场景压缩设计

> 在你的业务场景中，需不需要压缩 Agent 的上下文。如果需要，你是如何设计你的压缩方案的？为什么要这样设计？

### 题 2：ObservationMasking Token 实验

> 做一次 ObservationMasking token 实验。选一个典型长 session，然后比较后面这三个方案。
>
> - **方案 A**：保留完整历史
> - **方案 B**：保留 Action，mask 掉 N 轮以前的普通 Observation
> - **方案 C**：保留 Action + 错误 Observation，只 mask 普通 Observation
>
> 对比：
>
> 1. 省了多少 token
> 2. 最终答案有没有变差
> 3. Agent 是否还能记住自己做过哪些动作

### 题 3：敏感数据压缩测试

> 假设你的 Agent 会处理敏感数据，比如金融、医疗、合同、企业客户数据。请用合成数据设计一组测试样例，验证 compactor 压缩之后有没有破坏数据标签。
>
> 测试对象可以包括：
>
> - **敏感字段**：账户号、病历号、合同编号、客户名称
> - **数据标签**：PII / PHI / confidential / tenant-private
> - **权限标签**：仅当前 tenant 可见 / 仅内部员工可见
> - **错误标签**：异常交易 / 禁忌项 / 高风险条款
>
> 你要检查的是：
>
> 1. 压缩后敏感字段有没有被误写成普通信息
> 2. 数据分类标签有没有保留
> 3. tenant_id / user_id 有没有保留
> 4. 下游过滤器还能不能识别内容的敏感级别
>
> 最后给出你的 compactor 规则。

### 题 4：Anchor 演化 Trace 设计

> 假设你把 anchor 的每次更新都记录到 trace 总线，请设计一份最小日志结构，然后写出 3 个你想监控的问题。
>
> **不要写"看看 Agent 干了啥"这种泛泛问题，要写成能落到指标上的问题。**

## 附：本讲核心要点速查

| 关键词 | 含义 |
|--------|------|
| **Semantic Compaction** | 在长任务里维护 Agent 的工作记忆，确保它记得为什么走到这一步 |
| **双轴定位** | 感知 × 链式 |
| **三层压缩链** | L1 工具结果清理 → L2 Anchor 合并 → L3 极限摘要 |
| **anchor** | 五字段工作记忆锚点：intent / changes / decisions / excluded / next |
| **`excluded_approaches`** | 最关键的工程字段：已排除的方案，避免重复试错 |
| **ObservationMasking** | 把早期 Observation 替换成占位符，保留 Action |
| **`is_error`** | Turn 的关键标记，决定是否走错误保护路径 |
| **早期触发** | 长任务在 60-70%（高风险 50-55%）主动压缩 |
| **L3 退场信号** | 多次触发 L3 → 准备交接 / 开新 session / 转人工 |
| **handoff summary** | 给人类交接的结构化摘要（含 SLA deadline）|
| **三个观测指标** | level_3_trigger_rate / avg_compression_ratio / error_traces_preserved_per_event |
| **70/30 法则** | Agent 跑得稳不稳，70% 看推理、30% 看记忆 |
| **错误堆栈 = 测试套件** | 安全感来自关键证据保护（类比 Martin Fowler）|
