# 25｜护栏三明治：高风险行动的前中后防线

> **核心命题**：护栏三明治（Guardrail Sandwich）把一次高风险工具调用实现为 **PRE → TOOL → POST** 三阶段协议。
>
> - **前置守卫**在副作用发生前校验或规范化请求参数
> - **受控执行阶段**调用注册 Handler，记录原始输出或工具错误
> - **后置守卫**保留原始输出，再决定哪些内容可以发布
>
> **前置拒绝阻止工具运行，后置拒绝阻止结果发布**。三个阶段共同写入结构化守卫轨迹。

---

## 一、危险发生在两个时刻

V5-高风险输入输出实验包含两个独立切片：

### 1.1 第一切片：输入（前置守卫管辖）

```text
transfer_funds(emp="E0007", amount=999999)
```

工具名合法，参数类型也能被 Python 接受，**金额却远超本场景允许自动执行的 200000**。希望系统在工具运行以前发现问题。否则钱一旦转出，即使发现"金额过高"也已经晚了。

### 1.2 第二切片：输出（后置守卫管辖）

```text
{"msg": "已为 E0007 处理，账户 6222-0007-0049"}
```

只有工具返回以后，系统才看得到完整回复。**检查对象就从输入检查转到结果检查**：这个结果应该如何处理，能不能继续发布？

### 1.3 实验结果对照

| 配置 | 异常转账执行次数 | 原始输出含账号 | 可发布输出含账号 |
|------|---------------|--------------|----------------|
| **直接执行** | **1** | True | True |
| **护栏三明治（PRE/POST）** | **0** | True | **False** |

| 状态 | 含义 |
|------|------|
| `blocked_pre` | 工具**根本没有运行**，动作账中的转账次数是 0 |
| `blocked_post` | 工具已经返回，原始结果真实存在，**只是没有获准进入下游发布通道** |

## 二、护栏三明治模式的基本结构

```text
输入参数
  → 前置守卫（PRE）
  → 工具执行（TOOL）
  → 后置守卫（POST）
  → 可发布结果
```

> 这个模式名字非常形象，**前置和后置像两片面包一样把中间的工具调用夹住**。
>
> **同一项规则放在副作用发生之前还是之后，会起到完全不同的作用**。

### 2.1 工程化定义

> **护栏三明治（Guardrail Sandwich）**把一次高风险工具调用实现为 PRE → TOOL → POST 三阶段协议。前置守卫在副作用发生前校验或规范化请求参数，并分别记录请求参数与有效参数。受控执行阶段调用注册 Handler，记录原始输出或工具错误。后置守卫保留原始输出，再决定哪些内容可以发布。前置拒绝阻止工具运行，后置拒绝阻止结果发布。**三个阶段共同写入结构化守卫轨迹**。

## 三、前置守卫（PRE）：还有机会让副作用不发生

### 3.1 主循环

```python
for hook in self._applicable_hooks(tool_name, HookPhase.PRE):
    outcome = self._run_hook(
        hook,
        tool_name,
        effective_args,
        tool_output=None,
    )
    trace.effective_args = copy.deepcopy(effective_args)
    trace.pre_outcomes.append(outcome)
    if outcome.result == HookResult.BLOCK and hook.blocks:
        trace.final_status = "blocked_pre"
        trace.completed_at = _now_iso()
        return trace
```

> **Hook 是挂在固定执行点上的检查函数**。任何一道拦截型检查拒绝，工具都不会运行。

### 3.2 常见前置检查

| 检查类型 | 例子 |
|---------|------|
| 输入结构 | 字段类型、必填项 |
| 身份、租户和对象权限 | 谁可以改这张工资单 |
| 金额、频率和风险预算 | 单笔上限 200000 |
| 黑名单、账户状态和地区限制 | 受限账号名单 |
| 业务对象版本是否新鲜 | 版本匹配 |
| 幂等键是否存在 | 是否已提交过 |
| 审批票据是否仍与当前参数一致 | 旧审批失效 |

### 3.3 金额阈值钩子示例

```python
pre = GuardrailSandwich()
pre.register_tool("transfer_funds", transfer_funds)
pre.add_hook(
    amount_threshold_hook(
        field="amount",
        max_amount=200000,
    )
)
pre_trace = pre.run(
    "transfer_funds",
    {"emp": "E0007", "amount": 999999},
)
```

> 当发现 `999999 > 200000`，执行轨迹将进入 `blocked_pre`。**在当前教学实现里，amount 字段缺失时金额钩子会放行**，因此生产配置必须在它前面再放一道 schema 检查。**每道钩子负责一个明确字段，组合以后形成完整输入契约**。

### 3.4 字段规范化

> 前置钩子还可以做**字段规范化**。例如把字符串金额转成整数、把手机号转成统一格式、把用户输入映射成稳定业务 ID 等。
>
> **但这个动作可能会带来审计问题**：调用者传入的参数，可能已经不是工具最终收到的参数。

因此，**守卫轨迹同时保存请求参数和有效参数**：

```python
@dataclass
class SandwichTrace:
    """One sandwiched call's audit record."""
    tool_name: str
    args: dict[str, Any]                      # 调用者最初请求
    effective_args: dict[str, Any] = ...      # 前置守卫处理后的参数
    pre_outcomes: list[HookOutcome] = ...
    tool_output: Any = None                   # 原始输出
    released_output: Any = None               # 可发布输出
    tool_error: str | None = None
    post_outcomes: list[HookOutcome] = ...
    rollback_marked: bool = False
    final_status: str = "pending"
    started_at: str = ...
    completed_at: str | None = None
```

> **`args` 保存调用者最初请求，`effective_args` 保存前置守卫处理后真正送入工具的参数**。`tool_output` 与 `released_output` 则在后半程分别记录**原始输出和获准发布的输出**。

### 3.5 深拷贝的原因

```python
requested_args = copy.deepcopy(args)
effective_args = copy.deepcopy(args)
trace = SandwichTrace(
    tool_name=tool_name,
    args=requested_args,
    effective_args=copy.deepcopy(effective_args),
)
```

> 因为工具参数通常含有嵌套对象，**浅拷贝的情况下，前置守卫若修改 `payment.currency` 一类内层字段会连原始请求一起改掉**。这样我们本来希望保留的原始请求参数就随之消失了。

### 3.6 规范化示例

```text
请求参数（requested args）  = {"amount": "200"}
有效参数（effective args）  = {"amount": 200}
```

> 否则，事故发生以后，**守卫轨迹展示的是一份参数，工具执行的却是另一份参数，证据链就不清晰了**。

## 四、受控执行（TOOL）：异常不等于没有发生

### 4.1 受控执行代码

```python
try:
    trace.tool_output = self.tools[tool_name](**effective_args)
except Exception as e:
    trace.tool_error = f"{type(e).__name__}: {e}"
    trace.final_status = "tool_failed"
    trace.completed_at = _now_iso()
    return trace
```

> **但是在真实系统里，"调用报错"不等于"外部操作失败"**。

### 4.2 经典案例

- **银行转账**：银行可能已经完成入账，只是在返回结果时网络超时。调用者看到异常，但钱其实已经转出去了
- **发送邮件**：邮件服务器可能已经接收了邮件，只是返回确认信息之前，HTTP 连接断了。**再次发送，就可能让用户收到两封一模一样的邮件**

### 4.3 五种状态

> 生产系统不能只用"成功"和"失败"两个状态。**至少要区分**：

| 状态 | 含义 |
|------|------|
| `NOT_STARTED` | 尚未发起 |
| `STARTED` | 已经发起 |
| `SUCCEEDED` | 外部确认成功 |
| `FAILED` | 外部确认失败 |
| `UNKNOWN` | **结果仍不确定** |

> **最麻烦的是 UNKNOWN**。遇到这种情况，**不能马上重试**。系统应该拿着同一个幂等键，先去外部系统查询结果：
> - 外部系统确认成功 → 把本地状态补记为成功
> - 确认失败 → 才考虑重新执行
> - 仍然查不清楚 → 交给人工或专门的核实流程处理

> **简言之，异常只能说明"我没有收到明确结果"，不能说明"这件事没有发生"**。这是所有付款、下单、发邮件、发券等高风险工具都必须处理的问题。

## 五、后置守卫（POST）：管住发布，不假装撤销

### 5.1 后置守卫循环

```python
rollback = False
for hook in self._applicable_hooks(tool_name, HookPhase.POST):
    outcome = self._run_hook(
        hook,
        tool_name,
        dict(trace.effective_args),
        tool_output=trace.tool_output,
    )
    trace.post_outcomes.append(outcome)
    if outcome.result == HookResult.BLOCK and hook.blocks:
        rollback = True
```

> **后置守卫开始检查时，工具已经执行完了**。
>
> 比如，付款接口可能已经扣款，邮件可能已经发出，生产配置也可能已经修改。**后置守卫即使发现问题，也只能阻止系统继续使用或发布这个结果，不能让已经发生的事情自动消失**。

### 5.2 状态区分

| 状态 | 含义 |
|------|------|
| `blocked_pre` | **工具没有运行** |
| `blocked_post` | 原始结果不再发布，**外部影响可能已经发生** |
| `compensated` | **外部系统已经确认补偿成功** |

> 代码里的 `rollback_marked=True` 只表示系统发现了问题，接下来需要执行补偿，**它不表示补偿已经完成**。钱不会因为这个布尔值自动退回来，邮件不会自动撤回，生产配置也不会自动恢复。**系统还需要真正调用退款、撤回、恢复配置等补偿工具，并等待外部系统确认成功，才能把状态改成 `compensated`**。

## 六、钩子的顺序也需要设计

### 6.1 推荐的钩子顺序

同一个阶段里可能有很多钩子。它们**不能随便排列**，通常应该让**成本低、结果确定、最容易提前发现问题的检查先执行**：

```text
输入结构 → 本地权限 → 参数阈值 → 对象版本 → 外部名单 → 人工审批 → 工具函数
```

> 如果参数格式已经错了，就应该立刻拒绝，**没有必要再调用外部合规服务，更没有必要让人来审批**。因此，**钩子顺序本身就是一种策略**。好的顺序可以更早发现问题，减少外部调用和人工等待，也能降低整条执行链的成本。

### 6.2 人工审批后必须重检

> **人工审批还有一个特殊问题**：审批通过，不代表工具现在仍然可以执行。例如，申请审批时账户余额充足，对象版本也是最新的。但等待审批的半小时里，**余额可能发生变化，对象也可能已经被别人修改**。所以，审批结束以后，运行时**还要重新检查那些依赖实时状态的前置守卫**，不能拿着半小时前的检查结果直接执行。

### 6.3 phase + priority 决定稳定执行顺序

教学 Repo 使用 `phase` + `priority` 决定钩子的稳定执行顺序：

- `phase` 决定它属于前置还是后置阶段
- `priority` 决定同一阶段里谁先运行

```python
except Exception as e:
    result = HookResult.BLOCK
    reason = f"hook crashed: {type(e).__name__}: {e}"
```

### 6.4 失败即拒绝（Fail Closed）

> **如果一个正式启用的钩子自己崩溃了，系统默认拒绝继续执行**。这叫**失败即拒绝（fail closed）**。因为守卫本身已经无法完成判断，**系统不能擅自把它当成"检查通过"**。对于付款、改配置等高风险操作，宁可暂时拦住，也不能在安全状态不明时继续运行。

### 6.5 影子模式（Shadow Mode）

> 但是，一条新策略刚上线时，通常不应该马上拦截真实业务。否则规则写得不准，可能一次挡住大量正常请求。
>
> **更稳妥的做法是先使用影子模式**。影子模式会完整运行新规则，但**只记录"如果这条规则正式生效，它会拦住哪些请求？"，而不会真的改变业务结果**。

```python
if result == HookResult.BLOCK and not hook.blocks:
    return HookOutcome(
        result=HookResult.WARN,
        reason=f"[shadow] {reason}",
        ...
    )
```

> 影子钩子自己崩溃时，也不会阻断工具执行。等规则进入正式强制模式以后，**同样的崩溃就会真正阻止执行，形成 `blocked_pre` 或 `blocked_post`**。

> **影子运行期间，团队要统计命中率、误杀率、钩子耗时和业务分布**，明确负责人（owner）与策略版本（policy version），只有当数据达到预设标准，才逐步把规则从影子模式切换到强制模式。

## 七、护栏三明治的整体结构

| 角色 | 负责什么 |
|------|---------|
| **风险分级器** | 根据工具、对象和参数决定防护等级 |
| **策略注册表** | 保存钩子、版本、负责人和适用范围 |
| **前置守卫链（PRE Chain）** | 在副作用以前检查并规范化输入 |
| **受控执行器** | 作为原始工具的**唯一调用入口** |
| **后置守卫链（POST Chain）** | 验收输出与发布条件 |
| **守卫轨迹（Sandwich Trace）** | 保存请求参数、有效参数、策略判定和原始结果引用 |
| **效果账本（Effect Ledger）** | 保存外部回执与真实提交状态 |
| **补偿管理器（Compensation Manager）** | 推进冲正、重试和人工接管 |

> 当前 `GuardrailSandwich` 已经实现了工具注册、前置守卫、受控执行、后置守卫和守卫轨迹。**生产系统还需要补上两部分，效果账本和补偿管理器**。效果账本负责记录外部世界到底发生了什么；补偿管理器负责处理退款、撤回、恢复配置等后续动作。

### 7.1 引用监视器（Reference Monitor）

> 护栏三明治的思想和**操作系统安全中的引用监视器（Reference Monitor）**一致：
>
> 1. **每一次敏感访问都必须经过检查**
> 2. **调用者不能篡改或绕开检查点**
> 3. **检查机制足够小，可以被分析和验证**

### 7.2 运行时控制 > 提示词

> 教学代码为了方便展示，直接公开了工具注册表。因此，业务代码可以绕过所有守卫，直接执行：
>
> ```python
> sandwich.tools["transfer_funds"](**args)
> ```
>
> **生产系统应该隐藏原始 Handler，只向外暴露受控代理**。数据库、网络和云服务的权限，也应该只交给代理身份，而不是同时交给 Agent 进程。否则，**即使代码里有完整的守卫，Agent 仍然可以拿着旁路凭证直接访问外部系统**。

> **真正能够形成安全边界的，不是提示词，而是运行时控制**。受控代理、沙箱、网络策略和服务端授权，能够真正限制 Agent 可以访问什么、调用什么，以及一次操作能不能执行。**提示词里写一句"请勿绕过"，只能提醒模型，不能阻止模型越过边界**。

### 7.3 框架覆盖边界

> 2026 年，主流 Agent 框架已经开始把这套边界直接做进运行时。**以 OpenAI Agents SDK 为例**，工具守卫分为两类：
> - **输入守卫**：在工具执行前运行，用来判断这次调用是否允许发生
> - **输出守卫**：在工具执行后运行，用来检查工具返回的结果能否继续向下传播

> 输入守卫可以直接拒绝一次工具调用。输出守卫则可以拦截或替换工具结果，也可以抛出异常，让后续流程停止。
>
> 对于需要人工审批的工具，**审批通过以后，SDK 默认还会重新执行一次输入守卫**。

> **但这里还有一个容易忽略的问题**：框架提供了工具守卫，不等于所有执行路径都会自动受到保护。**目前，OpenAI Agents SDK 的工具守卫主要作用于 `function_tool`。托管工具、内置执行工具、任务交接，以及 `agent.as_tool()` 等其他路径，并不会天然经过同一套守卫**。
>
> 这意味着生产系统不能只问：我有没有给工具加守卫？**还要继续问：Agent 一共有多少条路径能够对外部系统产生影响？这些路径是否全部经过了等价的检查？**

## 八、组合绕行：单次调用安全，不代表整条行动安全

> 护栏三明治一次只能检查一个工具调用。但 **Agent 的风险，常常出现在多个工具的组合中**。

### 8.1 三个合法动作组成的越界

```text
read_profile
  → compose_email
  → send_email
```

- 读取员工资料：合法
- 生成邮件：合法
- 发送邮件：合法

**但如果 Agent 把刚刚读取的员工资料写进邮件，再发送给外部地址，整个过程就越界了**。

### 8.2 组合绕行的应对

> 这叫**组合绕行**：每一步都通过了检查，组合起来却产生了不允许的结果。因此，系统不能只看"当前调用是否合规"，**还要看信息在整条行动链中是怎样流动的**：

```text
员工资料（不可信 source）
  → 邮件正文
  → 外部邮箱（高风险 sink）
```

> **系统需要通过行动轨迹和工件来源证据，把这条传播路径连接起来，在最终发送之前阻止、冻结或升级审批**。

> OpenAI 在 2026 年 3 月 11 日发布的提示词注入防御实践中，也采用了类似的 **source-to-sink 思路**：安全系统不必保证识别出每一条恶意指令，但**应该限制不可信内容能够影响哪些高风险动作，以及哪些信息能够被发送到外部**。

## 九、契约漂移：工具升级了，守卫还活在旧版本

> 守卫判断工具调用时依赖的是**工具参数和返回值的结构**。

假设前置守卫按照 v1 检查：

```text
amount
recipient
```

但工具已经升级到 v2，新增了：

```text
amount
recipient
transfer_type
```

如果守卫不知道 `transfer_type` 的含义，就可能出现两种结果：

- **没检查新字段** → 错误放过了高风险操作
- **把合法的新请求当成异常** → 全部拦住

> 这叫**契约漂移**：工具接口已经变化，守卫仍然按照旧契约工作。解决办法是让工具、SDK、文档和守卫尽量从**同一份版本化契约生成**，并明确每条策略支持哪些工具版本：

```yaml
policy_version: 3
compatible_schema: v2-v3
```

> 如果高风险工具传来了未知版本，系统**不应该猜测字段含义后继续执行，而应该拒绝调用或转交人工处理**。

## 十、补偿幻觉：写下"需要回滚"，不等于已经恢复

> 后置守卫发现问题时，工具的副作用可能已经发生。例如，付款已经完成，系统随后发现订单状态不合法。此时把 `rollback_marked = True` 写进轨迹，**只能说明系统发现自己需要处理这件事，不代表钱已经退回**。

### 10.1 真正的补偿四步

```text
发现需要补偿
  → 创建持久补偿任务
  → 调用补偿工具
  → 确认外部系统已经恢复
```

### 10.2 状态区分（必须分清）

```text
rollback_marked != rollback_started
rollback_started != rollback_succeeded
rollback_succeeded != external_recovery_confirmed
```

> **即使退款接口返回成功，系统最好仍然查询银行或支付平台的最终状态**，确认资金确实已经退回。最危险的情况是：**补偿失败以后，系统却删除了补偿记录**。业务仍然处于 `PAID`，系统却忘记自己还欠用户一次退款。

> **生产补偿必须有持久状态机**。失败记录要继续保留，并配有重试预算、死信队列或人工核实流程，**直到外部系统确认恢复，才能真正结清**。

## 十二、收束行动模块

### 12.1 L0-L5 全模块矩阵

行动模块结束时，进入工作台第 25 讲，点击"运行全模块矩阵"。它把**五类受控故障放到六种累计配置下逐格运行**：

| 故障 | 对应模式 |
|------|---------|
| V1-越界改字段 | 最简工具集 |
| V2-跳读与双付 | 工具调度 |
| V3-中途超时后整批重跑 | 规划执行 |
| V4-污染工件向后传递 | 提示链 |
| V5-高风险输入输出 | 护栏三明治 |

### 12.2 矩阵对照

| 配置 | 新增控制 | 仍然暴露 |
|------|---------|---------|
| **L0-裸循环** | 无 | 全部五类故障 |
| **L1-最简工具集** | 缩小能力面 | V2、V3、V4、V5 |
| **L2-工具调度** | 增加执行准入 | V3、V4、V5 |
| **L3-规划执行** | 冻结完成事实，限制局部重排 | V4、V5 |
| **L4-提示链** | 增加段间事实闸门 | V5 |
| **L5-护栏三明治** | 增加前置与后置守卫 | **无** |

> 这张矩阵首先是一套**评测协议**。它用五类故障，逐层检验每一种控制到底解决了什么问题。每增加一种模式，就重新施加相应压力，观察原来的故障是否还会发生。

### 12.3 各模式边界不能替代

通过逐层加控制的方式，我们能验证每种模式能够提供什么保证，又不能提供什么保证。**各模式彼此不能替代，需要组合使用。它们共同构成行动运行时，但每一层只对自己的边界负责**：

| 模式 | 守住什么 | 不守住什么 |
|------|---------|----------|
| **护栏三明治** | 只守住一次高风险执行的前后边界 | 不了解整张计划，无法阻止局部步骤失败后整批重跑 |
| **规划执行** | 冻结已完成步骤，限制恢复范围 | 不会自动核验中间工件里的金额是否真实 |
| **提示链** | 拦住错误工件继续向后传播 | 不能单独决定某个付款工具是否应向当前 Agent 开放 |
| **工具调度** | 决定这一次能否调用 | 真正执行前仍需前置守卫核对金额/权限/对象状态 |
| **最简工具集** | 缩小能力面 | 不验证参数合法性 |

### 12.4 五道控制边界

> 所以，**这五讲是五道不同的控制边界**：
>
> - **最简工具集**：Agent 可以接触什么
> - **工具调度**：这一次允许调用什么
> - **规划执行**：整张计划怎样推进和恢复
> - **提示链**：中间工件怎样交接
> - **护栏三明治**：高风险动作执行前后怎样守住

> **到这里，行动模式组解决的是**：**怎样让 Agent 的行动被限制、被检查、可以恢复，并留下可以核对的运行事实**。
