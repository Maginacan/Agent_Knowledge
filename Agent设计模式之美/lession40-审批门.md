# 37｜审批门：让批准只对这一项动作有效

> **核心命题**：高风险动作生效之前，Agent 先把事实、差异和影响整理清楚，再请人作出判断；**人的一次点头只打开眼前这一扇门**。
>
> **一句话**：审批门不是把责任推给一个信息不足的人——**真正有用的监督是"人拥有足够的信息、权限和时间作出有效判断"**。
>
> **坐标**：治理 × 路由。**它属于治理**，因为它分配行动权；**它属于路由**，因为它不亲自完成业务动作，而是决定走自动路径、人审路径还是停止路径。

---

## 一、Agent 给审批带来什么新问题

任何在公司里工作过一段时间的人，都对审批不陌生：请假超 3 天主管批准、报销超额再走一级、供应商变更收款账户财务复核、新版本生产发布要等负责人放行、超常规折扣销售不能自己决定。这些流程长在 OA、邮件、财务、采购、权限和发布系统里——**长得不太一样，做的却是同一件事**：流程可以自己往前跑，到了责任边界，先停一下。

### Agent 时代的新来客

审批门很普遍，请假、报销、文档签署、业务流程批准都是企业 ERP 常见场景；GitHub 可以要求生产部署先经过指定 reviewer，还能禁止发起人自我批准；AWS Step Functions 允许工作流暂停，等人作出决定后再从原位置继续。

Agent 时代，审批门遇到了一种**会自己组织动作**的新来客：

| 传统工作流 | Agent |
| --- | --- |
| 申请单字段固定、节点固定、对应版本固定 | Agent 运行时决定调用哪个工具、使用哪些参数、处理多少对象、按什么次序执行 |
| 审批人看到的是已经成形的业务对象 | 用户只说一句"把这个月符合条件的退款处理掉"，Agent 先查订单→判断资格→生成清单→调用支付 |

### 让人紧张的不是省事，而是未知

Agent 的权力越来越大，会真正改变外部世界。Claude Code / Codex 会写好邮件但不发，问"我自己发？"——**有的时候它甚至补上一句："你告诉我一声，我帮你直接发"**。生产环节"让人看一眼"就更不够了。需要回答的是：

- 人看见了什么？
- 他批准的是**哪一版对象**？
- 批准以后 Agent 还能不能改参数？
- 等待期间数据变了怎么办？
- 这一声"同意"可以使用几次？
- 又能沿用到什么时候？

## 二、人和 Agent 在门前怎样交接

### 三方协作关系

> 一般的系统把这层关系做得较为粗糙：Agent 做到一半，弹一句"这是高风险操作，是否继续？"——如果人不知道它查了什么、为什么这样做、具体会改哪些对象，只能凭感觉点"批准"。出了问题以后，系统又说"这一步有人确认过"。**这不叫人类监督，只是把责任推给了一个信息不足的人**。

**真正有效的审批，应由三方各自完成一部分工作**：

- **Agent**：把动作做到"可审"，再来敲门。不应总让人替 Agent 补表、查 ID、核对加法；Agent 应先完成那些可以被工具和规则完成的工作，把事实整理成**紧凑的决策材料**。
- **审批人**：精力放在**价值判断、业务例外、重大影响和责任归属**上。并不是 Agent 一犹豫，就应该把问题送给人。
- **执行层**：等批准之后再执行，并对当前提案进行再核对。

### 一张不合格的审批单

供应商邮件："请把本月货款打到新账户"。付款 Agent 查到这家供应商已合作五年，本月金额也和平时接近，生成：

```text
支付本月供应商货款，是否批准？
```

这张审批单**几乎没有价值**。真正值得注意的不是"支付货款"，而是"**收款账户刚刚发生了变化**"。

### 一张合格的审批卡

一张合格的审批卡应把**最需要人判断的差异**放在最显眼的位置：

```text
项目                内容
────────────────    ──────────────────────────────────────
申请动作            向供应商 HZ-204 支付发票 INV-8821
金额                486,000 元
关键变化            收款账户由 ****2381 变更为 ****9042
                    变更时间：今天 10:42；过去 18 个月内第一次变更
核验结果            供应商主数据：已匹配
                    变更申请：已取得通过预先留存的联系人电话回拨确认：已完成
                    发票金额与采购订单：一致
Agent 建议          允许本次付款，但仅限发票 INV-8821
批准后的影响        将创建一笔不可自动撤销的银行付款指令
批准范围            仅本次、仅此账户、仅此发票，30 分钟内有效
```

> 审批人不需要翻阅 Agent 的全部思考过程。他需要看的是**业务对象、关键差异、证据来源、未决风险、外部影响和批准范围**。

### 证据不足 vs 需要审批

| 状态 | 含义 | 处理 |
| --- | --- | --- |
| **证据不足** | Agent 还没有把工作做完 | 继续查证、澄清或停止 |
| **需要审批** | 事实已基本清楚，只是影响和责任超过自动权限 | 进入审批门 |

> **一个提案进入人审之前，至少应当具备四个条件**：
> 1. 执行对象已经确认
> 2. 关键证据已经取得
> 3. 外部影响已经说明，能计算的部分也已经算清楚
> 4. 动作的可逆性和后续步骤已经说明
>
> 缺少任何一项，都不建议流转到审批环节。

## 三、审批的范围和审批者的角色

### "可以"的五个边界

人在聊天里说一句"可以"可能有很多含义：

- 这一次可以
- 这一批可以
- 今天之内可以
- 以后遇到类似动作都可以
- 允许 Agent 自己判断

> **审批门要把人的自然语言决定编译成一项有边界的许可**，这个边界要包含五个维度：
> 1. **谁**批准
> 2. 批准**哪一项**动作
> 3. 作用于**哪些对象**
> 4. 在什么**时间**内有效
> 5. 最多可以**使用几次**

### 业界做法
- **Codex 安全文档**：建议在"一次批准"和更宽范围间选择**能够完成任务的最窄授权**。
- **Claude Code**：区分临时批准、会话级授权、持久规则，以及 allow、ask、deny 不同权限结果。
- **新加坡 IMDA Agentic AI 治理框架**：把这种安排称为"**有意义的人类责任**"——重点不在于流程里出现过一个人，而在于这个人是否拥有足够的信息、权限和时间作出有效判断。
- **NIST 人机交互风险**：要明确区分 AI 系统中不同人的角色与责任——审批人、系统所有者、业务操作员和最终用户各有所指。

### 审批者也不一定永远是人

确定性规则可以处理**硬拒绝**和**明确放行**；边界请求还可以先交给**独立 reviewer agent**。

> OpenAI 在 Codex 的 auto-review 设计中，让单独的 reviewer agent 处理符合条件的升级请求，同时保持原有沙箱和审批策略不变——**它改变的是谁来检查，并没有取消边界本身**。重大外部影响、业务例外和责任性决定，仍然应当保留有意义的人类检查点。

## 四、审批门模式

### 工程化定义

> **审批门**（Approval Gate）位于一项具体动作生效之前。它根据动作主体、参数、资源、环境、影响和可逆性，在**自动放行、人工审批和拒绝**之间作出路由；进入审批后，**人的决定只绑定当前提案、当前策略、当前身份和有限的有效期**。

**坐标**：治理 × 路由。

### 关键执行流程

```text
可审提案形成 → 自动放行 / 人审 / 拒绝 → 
  ↓ (人审)
  人作出决定（绑定当前提案 + 策略 + 身份 + 有效期）
  ↓
执行 → 重新验证（TOCTOU 检查）→ 落地
```

> Agent 把准备执行的具体动作整理成要交给审批人的提案，其中包括**工具版本、规范化参数、资源范围、委托身份、策略版本和业务前置条件**。后面也要记录清楚谁批准了哪一个提案，最后实际执行了什么。

## 五、回到薪酬工作台

两位负责人已经批准了六月的工资清单。**准备执行时，Agent 又往里面加了两个人**。金额只多了几万元，原来的批准还能不能用？

### 实验设计

沿用第 36 讲的月末测试数据：

- 800 张工资单
- 798 张标为已付款
- 2 张标为已冲正

程序取出前 798 张组成一份 **13,706,097 元** 的清单，用它模拟一项准备提交的结算申请。

```bash
uv run python governance/payroll-lab/web_app.py --port 8767
```

申请由教学程序以 `payroll-agent` 名义提出。本次是整月批量结算，按工作台规则**需要两位负责人共同同意**：Alice 负责薪酬，Bob 负责资金。一个人同意还不够。

### 三阶段审批时间线

| 发生了什么 | 审批结果 | 为什么 |
| --- | --- | --- |
| 申请进入审批门 | 等待，`pending` | 需要两位负责人同意，还没人签字 |
| Alice 同意 | 仍在等待，`pending` | 薪酬负责人已确认，资金负责人还没有确认 |
| Bob 也同意 | 允许，`allowed` | 两个不同身份分别完成了所需确认 |

> 完整模式的双人会签。**审批角色、提案摘要、策略摘要和有效期同时出现**。

`allowed` 表示：这份 798 人、13,706,097 元的申请通过了审批。程序在这里停在审批结果，没有继续执行付款。

### 工件漂移：旧批准不再可用

点击"补回两张工资单"：从同样的初始数据重新跑一遍——**先取得两位负责人对原清单的批准**，然后把 E0007、E0012 两张单据加回来，再尝试使用刚才那份批准。

两张单据合计 **38,444 元**。加回来以后，申请变成 **800 人、13,744,541 元**。

- 审批人没换
- 原来的两次同意也还在
- **变的是他们没有看过的新清单**

程序为新清单生成新申请，把它和旧批准一起送到付款前的检查程序。左侧的"旧审批可用"变成"**否**"，右侧显示：

```text
拒绝：审批回执未绑定新提案
```

> 这句话的意思是：手里的批准对应原来的 798 人清单，**不能拿来执行现在的 800 人清单**。

工件漂移：**审批人的级别没有问题，问题出在批准对象已经换版**。

### 命令行输出

```bash
uv run python governance/payroll-lab/approval_gate_lab.py --changed
```

```text
== E0007 and E0012 restored after approval ==
   restored=E0007, E0012 delta=38,444.00
   artifact_digest=22d2af5795fa3f23 -> 97139db8d8fc35cd
   changed_digest=1b7669b5d5b231aa
   changed_scope=800 subjects, 13,744,541.00
   old_approval_authorizes=False
   adapter=payment adapter rejected invalid receipts: approval-gate
```

`delta=38,444.00` 是增加金额；`changed_scope` 是修改后的 800 人清单；`old_approval_authorizes=False` 表示旧批准不适用于新申请；最后一行说明付款前的检查也拒绝了它。

> 想再核对一次，可以打开页面上方的"证据账本"，选择 `payment_effects`——**这是本地实验记录实际付款动作的表，两种情况都没有新增付款记录**。

> **第二次运行的拒绝有明确原因**：两位负责人没有批准后来加进来的两张单据。下一步应当把新增人员和 38,444 元的差额交给他们重新确认。本实验演示到拒绝旧批准为止，没有自动完成新一轮审批。

## 六、为什么付款前还要再查一遍

> **审批门已经检查过了，为什么支付适配器还要再查？**

因为审批与执行之间有**时间差**。检查时成立的条件，使用时可能已经改变。这就是软件工程里的 **TOCTOU**（Time of Check to Time of Use）："检查时"和"真正使用时"之间出现了空档。

生产执行器在付款前至少要**重新确认四件事**：

1. 回执的决定是 `ALLOWED`
2. 回执绑定的提案摘要等于当前提案摘要
3. 回执绑定的策略摘要仍是当前生效版本
4. 回执尚未过期

核心契约集中在 `GovernanceReceipt.authorizes()`：

```python
def authorizes(
    self,
    proposal: ActionProposal,
    policy: PolicyRef,
    *,
    at: str,
) -> bool:
    if self.decision is not ControlDecision.ALLOWED:
        return False
    if self.proposal_digest != proposal.digest:
        return False
    if self.policy_digest != policy.digest:
        return False
    return self.expires_at is None or _instant(at) <= _instant(self.expires_at)
```

> 执行器应从可信存储读取回执。这段代码只检查批准是否仍对应眼前的提案和当前政策，使用次数另行处理。
>
> **账户状态、结算版本和资金余额等业务条件，也要在提交事务前重检，并用版本条件或锁防止检查后再次变化**。

## 七、"等待审批"是一种动态状态

> 审批会把一次 Agent 运行切成前后两段。前半段形成提案，后半段在批准后恢复。中间可能只等两分钟，也可能等两天。

任务等待期间，库存、余额、人员状态、代码版本和其他 Agent 的执行结果都可能变化。**"等待审批"必须成为一种持久化运行状态**，不能只停在某个 Web 请求或模型上下文里。

必须能找回来的信息：

```text
run_id                  # 哪一次任务
intent_digest           # 当时审批的提案
policy_digest           # 当时生效的规则
approval_id             # 对应哪一张票据
approval_status         # 等待、批准或拒绝
required_approver       # 谁还需要签字
expires_at              # 批准何时过期
resume_node             # 从哪里恢复
business_preconditions  # 恢复前需要重查的条件
```

恢复时，**不能拿着审批结果直接跳到工具调用**。运行时需要：

1. 重新读取当前提案、当前策略和关键业务状态
2. 再验证票据
3. 对象变了 → 重新生成提案
4. 票据过期了 → 重新申请
5. 条件仍然成立 → 才允许执行

> **AWS Step Functions** 的人工审批示例会暂停状态机，等待外部回调后再继续；**LangGraph** 的 `interrupt()` 配合持久化检查点和任务标识，也能保存状态并在收到外部输入后恢复。要留意，LangGraph 恢复时会从被中断节点的开头重新运行，因此**中断前做过的外部操作也要防止重复**。
>
> 框架提供暂停和恢复机制，**业务系统仍然要决定保存哪些事实、回来后重查哪些条件**。

## 八、对审批规则本身的审批

> **不仅付款要审批，修改"什么付款可以免审批"的规则，也要审批**。

比如原来超过 1300 万元的付款必须找人批准，现在有人想把上限提高到 3000 万元——这意味着更多付款可以自动通过。**这项改动不能由 Agent 自己决定**。

教学实验里，普通主管没有权限批准这种改动，必须由 **CFO** 点头。还可以采用更严格的安排，需要**治理负责人和风险负责人共同批准**。这样做是为了防止一种**绕行**：

> 一笔付款本来过不了，Agent 先把规则改松，再拿新规则批准自己的付款。

## 九、企业中的常见审批场景和策略

同一项能力在不同参数下，可能走完全不同的路线：

- "读取数据库"可能是查看一条订单，也可能是导出全部客户资料。
- "运行命令"可能是执行 `git status`，也可能是删除生产数据。
- "发放补偿"可能是给一位客户补一张 10 元优惠券，也可能是向 10 万名用户批量发券。

> **风险并不只和工具名称相关**。审批门需要看调用者、动作、目标资源、环境、对象数量、金额、外部可见性和可逆程度。

**企业真正需要建立的是一套委托尺度**：

- 什么动作可以自动做？
- 什么动作需要哪一级角色批准？
- 哪些动作无论谁批准都不能做？

### 审批门回答两个问题

1. 这项动作**要不要交给人**？
2. 需要交给**哪一个人**或**哪几个人**？

| 动作类型 | 审批路由 |
| --- | --- |
| 低额付款 | 薪酬主管批准 |
| 大额批次 | 财务控制人 |
| 收款账户变更 | 财务和资金团队分别确认 |

## 十、审批门使用注意事项

### 审批疲劳

> 最常见的是审批疲劳。使用 Claude Code、Codex 等 Agent 时，早期对一遍又一遍 Approve 感到厌烦，最后都不知道自己在 Approve 什么。直到 Claude Code 推出自动 Approve 常用命令的 Auto 模式。

**一扇成熟的审批门，目标是让人少审批，只看到值得点的那几次**。

系统应观察的指标：

- 人审比例
- 退回率、拒绝率
- 平均等待时间
- 票据过期率
- 对象变化导致的失效率
- 高风险动作绕过审批的发生情况

> 比如某条规则连续半年没有一次拒绝，可以检查它是不是还有必要进入人审；确认风险和适用条件已经稳定，再考虑自动放行。

## 十一、总结

审批门是企业很熟悉的一种结构。Agent 让它重新变得重要，是因为动作不再全部由固定流程预先写死。Agent 会在运行时形成提案、选择工具、组合参数，还会在暂停恢复后继续执行。

> **人机之间需要一次清楚的交接**：
> - Agent 负责把事情做到可审：对象明确、证据齐全、差异突出、影响可见
> - 人负责判断例外、权衡后果并承担相应责任
>
> 审批门的目标不是处处插人，**成熟的设计，是让日常动作安静地通过，少数高风险动作带着完整材料来到人面前**。

Agent 把事情准备好，人把责任想清楚，系统来绑定当前提案、当前策略、当前身份、限制时间和次数——这些都用于保证**当前审批的精准性和明确性**。

## 十二、思考题

1. 找到你所在系统里的一张审批单。它展示的是**动作摘要**，还是把**真正变化的字段单独标了出来**？
2. 哪些动作现在频繁进入人审，**其实已经稳定到可以自动放行**？哪些动作虽然金额不大，却因为不可逆或涉及个人权益，**仍应保留人审**？
3. 一项动作等待批准两小时以后，**哪些业务事实可能已经变化**？你的恢复路径会重新检查它们，还是直接沿用旧批准？
4. 如果 Agent 缺少关键证据，它现在会**继续查证、退回澄清**，还是把问题包装成一张审批单交给人？

## 十三、下一讲预告

人的批准完全正确，执行仍然可能出错：

- 程序可能重复提交
- 外部接口可能超时
- 一项合法动作也可能被放大成严重损失

> **既然错误无法完全消灭，怎样把一次错误最多能影响的金额、对象和次数提前圈住**？
