# 34｜对抗评审：让独立异议真正约束结果

> **核心命题**：评审意见只有绑定具体版本、带着证据进入发布闸，**才会从一条评论变成控制**。
>
> **一句话**：对抗评审增加的，是一条真正能够影响放行的责任链。**评审不是"有人看过"，而是"有人能够挡住"**。
>
> 真正的对抗评审落地要素：① 提案、举证、放行归不同责任主体 ② 异议结构化、可机读 ③ 状态机显式 ④ 任何修改都重新评审。

---

## 一、释题与开篇问题

上一讲把"子 Agent 是否隔离"拆成三个维度，聚合报告形成带条件的结论：

> 进程内 spawn Worker 使用独立会话，工具面可以收窄；**文件系统是否隔离，取决于 provider、沙箱与运行策略**。

主 Agent 看完后觉得不够利落，把主题定为："DeepSeek Harness 的子 Agent 默认完全隔离。"

报告发布前，有两位评审员分别检查了结论的适用边界：

- 一位指出：会话隔离不能直接推出文件系统隔离。
- 另一位补充：不同 provider 在上下文、工作区和工具范围上的语义并不相同。

基于这两条异议，评审环节重新拟定了更准确的主题：

> "DeepSeek Harness 的子 Agent 在会话、工作区与工具三个层面上分别怎样隔离。"

> 这个对抗评审流程的启发是：评审者提出反对意见的同时，**还要让这些意见进入合并与发布的状态转移条件**。
>
> 当存在未关闭的 blocker 时，候选稿不能从"评审中"进入"已批准"或"已发布"。修订者根据异议形成新版本后，新版本还要重新接受评审。

让对抗评审模式落地、建好发布闸，需要有一套详细的控制机制。

---

## 二、"有评审"和"评审生效"的差别

先跑工作台示例，展示对抗评审流程和注意事项。

- 配套实验：`collaboration/light_labs/editorial_review_lab.py`
- 配套工作台：`collaboration/light_labs/web_app.py`

```bash
git clone https://github.com/huangjia2019/agent-design-patterns.git
cd agent-design-patterns
python3 collaboration/light_labs/editorial_review_lab.py
```

### 第一次：评论型评审

```text
== review as comments ==
proposal=v1 blockers=2
published=true
problem=objections_recorded_but_not_enforced
```

候选工件接受了评审，评审意见被完整记录，但发布函数没有把这些意见纳入准入条件。两位评审员提出了两个 blocker，却没有继续检查：

- 阻断项是否已关闭？
- 这次评审是否覆盖必需风险？

这样的"已评审"只做了一半。

类似问题也常见于工程现场：

- PR 中有要求修改的评论，仓库仍允许强制合并。
- 安全扫描产生高危报告，流水线只检查构建是否成功。
- 合规 Agent 给出风险标记，付款函数只看审批字段是否存在。

> **系统具备评审功能，但评审没有获得控制效果**。

### 第二次：闸门型评审

把阻断意见正式接入发布条件：

```text
== review as gate ==
proposal=v1 published=false
proposal=v2 blockers=0 published=true
receipt=5432b6d2b684
```

只要存在未关闭的 blocker 就不能发布。修订者把结论改回带边界的表述，形成 v2；相同的评审规则重新执行，直到没有阻断项，发布闸才生成一张**绑定当前版本的回执**，确认进入发布流程。

也可以从网页版启动工作台观察：

```bash
python3 collaboration/light_labs/web_app.py
```

浏览器打开 `http://127.0.0.1:8098`，左侧选择"34 对抗评审"，点击"运行对照实验"：

- **左侧**：两条 blocker 都被记录，发布入口只验证正文存在，v1 仍然上线。
- **右侧**：发布函数必须获得一张**有效评审回执**。v1 因阻断项未关闭被拒绝；修订后的 v2 重新接受评审，才获得自己的发布资格。

> **评审结果需要进入状态转移条件**。

## 三、对抗评审到底是什么

模式名称中的"对抗"指**目标函数和责任位置不同**：

- **提案者**：任务是形成一个能向前推进的候选版本。
- **评审者**：任务是**主动寻找**足以阻止当前版本进入下一阶段的失败条件。

一个负责证明"可以做"，另一个负责检查"凭什么可以做"。

### 工程化定义

> **对抗评审**，是把**提案、举证与放行**分配给相对独立的责任主体，由评审者针对某一版候选工件提出带规则和证据的**结构化异议**，再由**确定性闸门或授权裁决者**决定退回、修订、放行或升级人工。

定义包含四个不可缺少的对象：

| 对象 | 缺失后果 |
| --- | --- |
| **候选工件** | 没有它，评审对象会在过程中漂移 |
| **结构化异议** | 没有它，评论无法稳定进入机器规则 |
| **裁决策略** | 没有它，blocker 只能停留在界面上 |
| **版本回执** | 没有它，旧评审可能被借给已经改过的新工件 |

对抗评审位于**协作维度**，是因为提案、质疑和放行由不同责任主体承担——即使底层使用同一个模型，这几个角色也要在身份、上下文、数据访问或权限中形成明确边界。

对抗评审位于**循环拓扑**的原因是：评审一旦拒绝当前版本，系统要经过一条完整路径：提案 → 评审 → 退回 → 修订 → 重新评审。新版本不能继承旧版本的评审结论。每次修改都会形成新的被审对象，必须重新进入评审循环。

> 对抗评审的循环不是让多个 Agent 无休止地互相评论，而是让每个新版本都**重新获得一份属于自己的裁决**。

### 四个角色

一套完整的对抗评审通常包含四个角色，分离**提案权、举证权、裁决权**三种权力：

| 角色 | 职责 |
| --- | --- |
| **提案者** | 提出方案 |
| **评审者** | 指出哪条失败条件已经被触发 |
| **裁决者 / 放行闸门** | 决定该版本能否进入下一阶段 |
| **修订者** | 根据异议产生新版本 |

> 这与财务流程中的 **maker-checker** 原则相近：经办人发起付款，复核人检查依据，最终授权仍受额度、身份和策略约束。

## 四、它和生成评审模式的不同点

生成评审（反思模块）和对抗评审（协作模块）名称相近，服务目标不同。

**生成评审**主要服务当前产出：

- 生成器写一版，批评者指出问题，修订器继续改。
- 适合报告、代码和计划的质量提升。
- 批评者可以是同一运行时中的另一个角色。

**对抗评审**把要求再往前推一步：

- 评审者是协作边界上的**独立责任主体**，异议会影响工件能否放行。
- **错误代价、审计要求与职责分离**，是从生成评审升级到对抗评审的主要理由。

| 维度 | 生成评审 | 对抗评审 |
| --- | --- | --- |
| 关心 | 当前产出的质量改进（"还能不能写得更好"） | 状态是否能达到转移的标准 |
| 检查 | 还能怎么改 | 当前版本是否已满足放行条件；是否存在任何不能被其他优点抵消的硬伤 |
| 作用范围 | 同一运行时内的角色 | 协作边界上的独立责任主体 |

二者**可以组合**：

- 外层对抗评审发现 blocker 后，修订过程内部可以使用生成—批评提高修复质量。
- 修订完成后，外层仍要对新版本重新评审。

> **内层负责把东西改好，外层则负责决定改好的东西能否发表**。

## 五、把评审独立性结构化

"把评审独立性结构化"解决的是：**评审必须覆盖不同的角度**。

### 多 Agent ≠ 独立

"用了多个 Agent"本身**不能**证明评审独立。多个 Agent 也可能：

- 使用同一模型。
- 继承同一段上下文。
- 读取同一份错误摘要。

最后在同一个盲区里互相确认。

### 真正关注的是"独立证据条件"

关注的是**来自不同评审者相互独立的证据条件**。

> **跨模型 ≠ 事实独立**。两个不同模型都只读一份错误月报，仍然可能一起批准错误数字。反过来，同一个模型在提案阶段只读月报，在评审阶段读取独立数据库查询，也可能形成有价值的事实对抗。

因此，独立性应该是一组**可以被审计的结构证据**：

1. 谁在评
2. 它看到了什么
3. 它**没有**继承什么
4. 它从哪里取得事实
5. 它能不能给自己放行

任务风险越高，对这些证据的要求越严格。

## 六、风险覆盖面和评审者的数量

只是多加上几位评审者，也**不代表风险覆盖更完整**。三个评审者可能都在检查文风，没有人核对事实和权限。

上线以前，可以先通过一张风险覆盖表做个分析：

| 评审者 | 负责的风险面 | 删除后会失去的观察 |
| --- | --- | --- |
| 评审者 A | 文风/可读性 | 文风失去独立观察 |
| 评审者 B | 事实核查 | 事实失去独立观察 |
| 评审者 C | 权限/合规 | 权限失去独立观察 |

这张表回答的是**每位评审者为什么存在**：

- 删除其中一位后，哪一类风险会失去观察者？
- 如果答得出来，它就**不能被取代**。
- 如果回答不出来，它可能只是"再看一眼"的重复角色，**可有可无**。

## 七、回执必须绑定正在放行的那一版

评审过程中可能发生状态变化。用显式状态机表达对抗评审流程：

```text
DRAFT
   ↓
IN_REVIEW
   ├── CHANGES_REQUESTED
   │        ↓
   │     REVISED
   │        ↓
   │     IN_REVIEW
   │
   ├── ESCALATED
   └── APPROVED
              ↓
           RELEASED
```

一旦 `APPROVED` 工件发生修改，状态应立即失效：

```text
APPROVED
    + mutation
        ↓
      STALE
        ↓
    IN_REVIEW
```

如果评审发生在上午十点，发布发生在十一点——**中间候选内容、依赖数据或规则版本都可能变化**。那么发布入口必须重新核对：

> "现在拿到的工件，就是刚才评审的那一版。"

也就是说，**回执同时绑定**：

- **提案身份版本**
- **正文与来源引用的联合摘要**

正文哪怕只改一个字，或来源引用被换掉，摘要都会变化。因此**旧的回执不能被传递给最新的工件**。

> 审批状态不是工件的**永久属性**，而是"某个版本在某套规则和证据下曾经通过"的**历史事实**。这个事实不一定持续稳定，它可能随着时间流转和状态变化。

## 八、小结

对抗评审增加的，是一条**真正能够影响放行的责任链**：

- 提案者给出候选。
- 评审者提出带规则和证据的异议。
- 修订者产生新版本。
- 闸门决定退回、放行还是升级。

只要工件发生变化，**就重新评审**。

### 适用场景

对抗评审最适合那些**错误真的会进入下一步业务，而且单靠程序规则又很难完全判断**的场景：

- 付款需要 maker-checker。
- 公开报告的重要结论需要独立核查。
- 安全方案需要有人专门从攻击面挑问题。
- 法律、医疗和合规判断需要职责分离。
- 代码即使测试通过，也可能仍存在权限扩大或架构副作用。

尤其适合处理那些**需要理解"意思"**的内容风险：一句话有没有说过头、结论是否超出证据能够支持的范围、几个分别正确的局部事实拼在一起后有没有被概括成错误结论。这类问题字段可能是齐的、格式也完全正确，普通 Schema、类型检查和规则校验都发现不了。

> 对抗评审更适合"意思类"问题；格式、类型、余额、身份、版本绑定这些能明确写成规则的检查，交给**确定性程序**通常更稳。**两者配合，比把所有检查都交给 Critic 更可靠**。

### 按风险分层

| 风险等级 | 处理方式 |
| --- | --- |
| 普通内容 | 一个 Critic 足够 |
| 重要工件 | 增加独立证据和确定性闸门 |
| 真正高风险的动作 | 保留人工授权 |

> **关键不是多一个评审者，而是这位评审者到底增加了什么**：新的风险覆盖、新的证据来源，还是新的控制权。

## 九、思考题

1. 你的 Critic 提出 blocker 以后，**真的能阻止发布、付款或部署**吗？
2. 修订产生新版本以后，会**重新评审**，还是继续沿用旧回执？
3. Critic 相比提案者，**到底多看到了什么新的证据或风险**？
