## 一句话核心

> **记忆模式 ≠ 让 Agent 记住东西这么简单。它真正要解决的是：防止长程任务在时间中漂移。**
>
> Agent 需要记住的是那些**会影响后续行动的承重信息**：关键判断、依赖路径、失败方案、禁止动作、未完成假设、下一步行动的边界。

## 一、电影开场：《记忆碎片》

### 1.1 主角的隐喻

> 不知道你是否看过电影《**记忆碎片**》？里面的主角患有**短期记忆障碍**，新的记忆只能停留很短时间，无法稳定变成长记忆。
>
> 为了追查他妻子被谋杀的真相，他只能依靠外部线索：**照片、纸条、纹身**，把关键事实留在身体和物件上。
>
> 换句话说，他给自己搭了一套**外部记忆系统**。

### 1.2 这和 Agent 很像

> 这和 Agent 很像。大模型在一次会话里看见了很多东西，做了很多判断，也可能踩过很多坑。
>
> **但如果这些东西没有被写到外部记忆里，窗口一关，它就很难在下一轮继续使用**。
>
> 于是我们给 Agent 设计 **scratchpad、进度追踪、长期记忆、失败日记**，本质上也是在给它**留下照片、纸条和纹身**。

> **这一模块讨论的，就是怎样让今天的 Agent，用得上昨天它曾经学到的东西**。

## 二、记忆模块到底关注什么

### 2.1 传统软件 vs 大模型

| 维度 | 传统软件 | 大模型 Agent |
|------|----------|--------------|
| **状态持久化** | 进程崩了有数据库兜底 | **没有外部记忆，模型权重不会因为一次会话自动改变** |
| **会话恢复** | 请求断了有 session / checkpoint | 上下文窗口里"记住"的东西 → **窗口一关，会话一结束，Agent 就重置** |
| **结果** | 重启后照着状态恢复 | **变回一个对你和你的项目都不熟悉的陌生人** |

### 2.2 反例：auth.py 重构 Agent

**任务背景**：

> 一个负责代码重构的 Agent，任务是把一个臃肿的 `auth.py` 拆成三个模块。
>
> 在前面几轮分析里，它发现：
>
> - `UserSession` 和 `PermissionCache` 之间有一个**循环依赖**
> - 这个依赖**横跨四个文件**
> - 应该**先抽出一个共享的 `types.py`**
> - 如果直接动 `UserSession`，会影响 **43 个测试用例**

**它只写了一份摘要式进度**：

```
## Session 3：auth.py 拆分准备
已完成：
- 梳理 auth.py、session.py、permission_cache.py、permissions.py 的 import 关系
- 确认 UserSession 与 PermissionCache 之间存在循环依赖
- 建议先引入共享 types.py，再继续拆分 auth.py
待继续：
- 开始移动 UserSession 相关代码
- 跑 auth regression suite
```

**这份记录的问题**：

| 缺失信息 | 影响 |
|----------|------|
| 循环依赖的**具体路径** | 下一轮 Agent 不知道哪里打结 |
| **已经被排除的错误做法** | 下一轮 Agent 可能重新尝试 |
| **下一步不要先移动 UserSession** 这个**禁止动作** | 下一轮 Agent 直接踩坑 |

**最危险的是**：

> 最后一行"**开始移动 UserSession 相关代码**"还把下一轮 Agent **往危险方向轻轻推了一把**。

### 2.3 长程任务的漂移

> 这是**长程 Agent 系统目标和任务漂移**的一个具体展现。
>
> 长程任务**不是一次推理完成的**，而是在多轮会话、多次压缩、多次交接中逐步推进的。
>
> - 每一次摘要都会损失一点细节
> - 每一次交接都会改变一点语义
> - 每一次续接都会让 Agent 根据当前看到的残缺信息重新解释过去
>
> **最初明确的工程判断，经过几轮传递之后，可能从"先抽 types.py，禁止先移动 UserSession"，漂移成"移动 UserSession 时顺手补 types.py"**。

### 2.4 漂移的代价

> 下一轮会话开始时，context 是空的。Agent 读到这份进度摘要：
>
> - 看到了"建议先引入共享 types.py"
> - 也看到了"开始移动 UserSession 相关代码"
>
> 它做了一个很合理、也很危险的解释：**先把 UserSession 移到新模块，再在移动过程中顺手补 types.py**。
>
> 结果是**一大批文件被改坏，CI 无法继续，项目不得不回滚**。

### 2.5 记忆的真正使命

> 所以，**记忆模式并不是我们字面上所想的"让 Agent 记住东西"这么简单，它真正要解决的是防止长程任务在时间中漂移**。
>
> Agent 需要记住的是那些**会影响后续行动的承重信息**：
>
> 1. **关键判断**
> 2. **依赖路径**
> 3. **失败方案**
> 4. **禁止动作**
> 5. **未完成假设**
> 6. **下一步行动的边界**

> 长程 Agent 会基于**被压缩过、被改写过、已经漂移的记忆继续行动**，而且**行动得非常自信**。
>
> 记忆设计的意义，就是把这些**容易漂移的判断固定下来**，让下一轮 Agent 接手时：
>
> - 不只是知道**"做过什么"**
> - 还知道**"为什么这么做"**
> - **"什么不能做"**
> - **"哪些坑已经踩过啦"**

## 三、记忆是 PRA 循环里的时间维度

### 3.1 PRA 循环回顾

> 除了双轴框架，这门课贯穿始终的另一张图是 **PRA 循环**：**感知（Perception）、推理（Reasoning）、行动（Action）**。

| 环节 | 问题 |
|------|------|
| **感知** | 这一轮 Agent **看到了什么** |
| **推理** | 它**如何做判断** |
| **行动** | 它**如何改变外部世界** |
| **记忆** | **时间问题**：上一轮的感知、推理和行动，**怎样影响下一轮** |

> **记忆把 PRA 一起拉到时间维度上**，让今天的 Agent 能用得上昨天那个 Agent 留下的判断，**站在上一轮的肩膀上继续前行**。

### 3.2 1945 年的预演：Vannevar Bush 的 memex

> 1945 年，**Vannevar Bush** 在《**As We May Think**》里设想过一台叫 **memex** 的机器：
>
> - 能存下一个人的文档
> - 也能存下**文档之间的联想路径**

> memex 没有真的造出来，但他提出的愿景现在仍然成立：
>
> **光存得多没有意义，真正有价值的是需要时能取出来**。

> 今天每一个**向量数据库、每一条 RAG 管道、每一份失败日记**，都是这个愿景在大模型时代的**局部实现**。

### 3.3 四种东西要分清楚

Agent 的记忆至少有四种东西要分清楚：

| 类型 | 含义 |
|------|------|
| **working memory（工作记忆）** | 当前 context window 里**正在被模型使用的信息** |
| **scratchpad（草稿纸）** | 当前任务里的**工作台**，用来暂存中间判断、工具结果分析、规则核对、下一步计划 |
| **episodic / semantic / procedural memory**（经验/语义/程序记忆）| **事件、知识、流程**这些跨会话保留的长期记忆 |
| **memory trace（记忆追踪）** | 记录一次记忆如何被**写入、取回、使用和淘汰**的仪表盘 |

> 这里**最容易被低估的，就是 scratchpad**（中文可以翻译成"**草稿纸**"）。

## 四、Scratchpad（草稿纸）：记忆工作台

### 4.1 草稿纸的角色

> scratchpad 在 Agent 系统里是一张**工作台**：
>
> - 工具调用刚回来
> - 规则还没核完
> - 几个方案还没排除
> - 下一步动作还没决定
>
> 这些东西**先放在工作台上**。
>
> 等这一轮任务收束，再决定：
>
> - 哪些该**扔掉**
> - 哪些该**写进进度追踪**
> - 哪些该**升级成失败日记**
> - 哪些该**进入长期知识库**

> **重点是把工作台上的关键判断蒸馏成下一轮还能用的记忆**。

### 4.2 2026 工业界的三条线索

> **2026 年的 Agent 工程开始重视这张"记忆工作台"**。

| 来源 | 机制 |
|------|------|
| **Anthropic "think" tool** | 把 thinking 做成一种工具：不获取新信息，也不修改数据库，只是把思考追加到日志里，用来处理复杂工具链、政策密集环境和顺序决策 |
| **context editing + memory tool** | 把"**删掉 stale context**"和"**把关键信息存到 context 外**"分成两件事 |
| **OpenAI reasoning models** | 文档提到：reasoning tokens 默认不会直接留在上下文里，多轮工具调用时，需要**显式传回 reasoning items 或等价状态** |
| **LangGraph** | 把短期记忆做成 **thread-level state**，用 checkpointer 让一次会话可以恢复 |

### 4.3 现代 Agent 的记忆生命周期

```
context window 上下文窗口
       ↓
scratchpad 草稿纸
       ↓
structured trace 结构化追踪
       ↓
long-term memory 长程记忆
       ↓
retrieval / replay / forgetting 检索 / 重放 / 遗忘
```

| 阶段 | 解决什么 |
|------|----------|
| **上下文窗口** | "这一刻看见什么" |
| **草稿纸 scratchpad** | "这一刻正在怎么算" |
| **结构化追踪** | "这一轮到底发生了什么" |
| **长程记忆** | "哪些经验值得跨会话留下来" |
| **检索 / 重放 / 遗忘** | "下一次要不要把它拿回来，以及什么时候该让它过期" |

### 4.4 scratchpad.write 示例（auth.py 案例）

```python
scratchpad.write({
    "task": "拆分 auth.py",
    "current_finding": "UserSession 与 PermissionCache 循环依赖，跨 4 个文件",
    "cycle_path": [
        "auth.py",
        "session.py",
        "permission_cache.py",
        "permissions.py",
        "auth.py",
    ],
    "tested_attempt": "先移动 UserSession 到 session.py",
    "observed_failure": "43 个 auth regression tests 失败",
    "candidate_decision": "先抽共享 types.py",
    "do_not_do_next": "不要先移动 UserSession",
    "needs_persist": True,
})
```

### 4.5 memory.write 示例（沉淀到长期记忆）

```python
memory.write({
    "goal": "把 auth.py 拆成三个模块",
    "finding": "UserSession 与 PermissionCache 存在循环依赖，跨 4 个文件",
    "cycle_path": "auth.py -> session.py -> permission_cache.py -> permissions.py -> auth.py",
    "decision": "先抽出共享的 types.py，再继续拆分 auth.py",
    "do_not_do": "不要把 UserSession 作为第一步移动，已验证会触发 43 个测试失败",
    "evidence": "auth regression suite, Session 3 scratchpad",
    "next_step": "下一轮第一步：建 types.py，不要先碰 UserSession",
})
```

### 4.6 草稿纸 vs 摘要式进度

> 同样一轮推理，**摘要式进度记录没有完全丢信息**，但它丢掉了**最值钱的可执行约束**。
>
> 新版记法先把中间判断放到工作台，再把能复用的部分沉淀到长期记忆。

> 这和只写"**接口调用失败**"却没有留下 **error code** 很像。人回头看，大概知道发生过什么；下一轮 Agent 接手时，**却少了最关键的诊断入口**。

### 4.7 重要告诫

> 还有一点，就是**不要把模型原始的思考过程（raw chain-of-thought）当成业务记忆**。
>
> 企业系统需要的是**可验证、可审计、能续接的判断**，而不是模型内部念头的原样留档。

## 五、各种类型的记忆

### 5.1 Agent 记忆要解决的三个传统软件问题

| 问题 | 含义 | 传统软件机制 |
|------|------|--------------|
| **① 状态持久化** | Agent 被打断之后，要记得自己刚才在干什么 | 数据库状态、session、checkpoint |
| **② 知识检索** | Agent 要访问的信息远超上下文窗口能装下的量 | 数据库、搜索索引、文档系统 |
| **③ 经验累积** | Agent 应该从过去的执行里学到东西，下次少踩坑 | **传统软件里没有完全等价的机制**；最接近的是**测试套件和事故复盘** |

### 5.2 学术框架的两个里程碑

| 年份 | 框架 | 核心思想 |
|------|------|----------|
| **2023** | **CoALA**（Sumers et al.）| 把语言 Agent 放进一个**认知架构**里看，里面有**工作记忆**，也有**情节、语义、程序**等长期记忆 |
| **2023** | **MemGPT**（Packer et al.）| 把记忆**类比成操作系统的虚拟内存**，让 Agent 像管理内存分页一样，决定什么留在上下文里、什么换出到外存 |

### 5.3 2026 工业产品矩阵

| 系统 | 路线 |
|------|------|
| 一些系统 | 强调**文件式记忆工具** |
| 一些系统 | 强调**线程级别的检查点** thread-level checkpoint |
| 一些系统 | 强调**时序知识图谱** |
| 一些系统 | 强调**写入阶段先做抽取和压缩** |

### 5.4 四个记忆工程问题（核心追问）

> 真正的难点会落到**四个问题**上：

| # | 问题 |
|---|------|
| 1 | **什么信息只该留在 context window 里？** |
| 2 | **什么信息该先放进 scratchpad**，等任务收束再决定去留？ |
| 3 | **什么信息应该写进长期记忆，并在需要时准确召回？** |
| 4 | **什么信息已经过期，应该被淘汰或降权？** |

> 把这四个问题放回 PRA 循环里就很清楚了：
>
> **推理的质量，既取决于模型当下怎么想，也取决于记忆有没有把过去那些正确判断，完好地交到它手里**。
>
> 所以**记忆更像经验工程，存储只是它的底座**。
>
> 一个 Agent 的经验，要看它从这些 token 里**留下了什么**，又**在恰当的时候取回了什么**。

## 六、记忆模式组中的四种模式

### 6.1 四个字概括："架 / 取 / 录 / 省"

| 模式 | 字 | 解决什么 | 记忆类型 |
|------|------|----------|----------|
| **分层保留**（[[lession14-分层保留]]）| **架** | 做记忆系统，最先要定下来的就是**层级** | 工作记忆（working memory）|
| **检索增强**（RAG）| **取** | 记忆架构里最大的那一层，通常是**语义记忆**，需要时取回来 | 语义记忆（semantic memory）|
| **进度追踪**（Progress Tracking）| **录** | 管的是**事件**，每一步做了什么、为什么这么做、结果如何 | 情节记忆（episodic memory）|
| **失败日记**（Failure Journals）| **省** | 这里的"省"不是节省，而是**反省**：把失败做成一类特殊的记忆 | 失败记忆（failure memory）|

### 6.2 四个模式详解

**分层保留 — 架**：

> 做记忆系统，最先要定下来的就是层级。先想清楚**分几层、每层放什么**，再去写代码。
>
> - CoALA 给了认知架构的分层
> - 计算机里的**内存层级（memory hierarchy）**体现了从 L1 缓存到外存的设计
> - Claude Code 的记忆体系也是：
>   - **热**的一层永远在线
>   - **温**的一层按需加载
>   - **冷**的一层留在外存，用工具去取

> **层级不能太少，否则什么都堆在一起；也不能太多**，否则每一层都要维护一套晋升和淘汰规则。

**检索增强 — 取**：

> 记忆架构里最大的那一层，通常是**语义记忆**。
>
> 语义记忆**不可能全部塞进上下文窗口**，只能在需要时取回来。
>
> 过去很多系统把 RAG 当成万能入口，什么问题都先检索一遍。
>
> 到了 Agent 系统里，**RAG 要和"按结构直接读""按路径打开文件""按工具查询状态"科学分工**，而不是包打天下。

**进度追踪 — 录**：

> 它管的是**事件**，而不是知识。
>
> Agent 跑一个长任务，**每一步做了什么、为什么这么做、结果如何**，这些都是**情节记忆（episodic memory）**的原料。
>
> **开篇那个 auth.py 事故，对症的药就在这一讲**。
>
> 写进度的关键，不是记一行"做了什么"，而是写下：
>
> - **"为什么这么做"**
> - **"排除了什么"**
> - **"下一步该怎么办"**
> - **"下一步不能做什么"**

**失败日记 — 省**：

> 这里的"省"，不是节省，而是**反省**。
>
> Agent 每一次踩坑，都是宝贵的学习信号。
>
> 但这些信号**默认会随着会话结束一起消失**。
>
> 失败日记把失败做成一类特殊的记忆，**在下次遇到类似情境时主动召回**。

### 6.3 不单独安排"程序性记忆"的原因

> 可能你已经注意到，记忆模式组里没有单独安排"**程序性记忆**"一讲。
>
> "**程序性记忆**"把会做的活儿固化成可复用流程，也就是**技能包（Skill Package）**模式，是经验沉淀的高级形态。
>
> 它的**封装、复用和持续改进**，**更适合放到反思模式组里讲**。

### 6.4 完整映射

| 记忆类型 | 对应模式 |
|----------|----------|
| **工作记忆（working memory）** | 分层保留 |
| **语义记忆（semantic memory）** | RAG 和其他检索机制 |
| **情节记忆（episodic memory）** | 进度追踪 |
| **失败记忆（failure memory）** | 失败日记（episodic 中最值得主动召回的一类）|
| **程序性记忆（procedural memory）** | Skill Package（反思模块）|

## 七、四个记忆工程问题（2025-2026）

### 7.1 问题一：记忆框架到底选哪家？

| 框架 | 路线 |
|------|------|
| **Letta** | 让 Agent 自己在 core / archival / recall 等记忆层之间搬运信息 → **Agentic 记忆操作系统** |
| **Mem0** | 强调**单遍层次抽取**和**多信号检索**，试图把记忆的整理工作**前移到写入阶段** |
| **Zep** | **时序知识图谱**，擅长表示"**事实随时间怎么变**" |
| **Anthropic Memory Tool** | 更底层，Agent 直接读写一个**持久化记忆目录** |

> 可以尝试看看哪个框架更适合你的场景，或者自己设计记忆架构。
>
> **但不建议同时上两套记忆系统**。因为记忆有**单一事实来源**的问题。

### 7.2 问题二：长程 Agent 如何记忆？

| 来源 | 核心 |
|------|------|
| **论文《Episodic Memory is the Missing Piece for Long-Term LLM Agents》** | 长程 Agent **不能只记住抽象事实，也要记住具体事件** |
| **Anthropic Managed Agents → Dreaming** | 把**记忆整理从会话内搬到会话间** |

> 对我们的启发是：**记忆存下来以后，还要经历整理和消化**。

### 7.3 问题三：向量数据库还是文件系统？

> **Manus 团队**把**文件系统**当成 Agent 的**外部化上下文**来用。

| 数据形态 | 推荐存储 |
|----------|----------|
| **结构化记忆**：任务清单、配置、标准流程、进度文件 | **文件系统**（简单、可调试、可解释）|
| **非结构化大库**：用户历史对话、文档全文、知识库 | **向量数据库或图数据库** |

### 7.4 问题四：记忆该让 Agent 自己写自己读，还是由框架强制规范？

| 模式 | 优点 | 缺点 |
|------|------|------|
| **Agent 自管**（自己写自己读）| 灵活 | 可能写出**垃圾记忆、读到错误记忆** |
| **框架强规范** | 安全 | 重，改起来贵 |

> **比较健康的中间态**：**Agent 提议、框架定规矩**。
>
> - 让 Agent **判断该记什么**
> - 框架**约束按什么 schema 记**
> - 最后再用 **trace 看这些记忆有没有真的被用上**

### 7.5 模块总结

> 学完这一模块，你会发现，所谓"让 Agent 拥有记忆"，其实是在设计一套**经验的沉淀秩序**：
>
> - 什么**值得留**
> - 什么**留多久**
> - 什么时候该**取回来**
> - 什么时候该**让它过期**
>
> **记忆不是存储的堆叠，而是经验的治理**。

## 八、Memory Trace：给 Agent 的记忆装一块仪表盘

### 8.1 为什么需要 Memory Trace

> 像上一模块的感知追踪（Perception Trace）一样。我们也需要做 **Memory Trace，记忆追踪**。
>
> **没有 Memory Trace，你很难发现错误的根因**，因为最终回答里看不出来 Agent 当时手里到底有没有相关记忆。
>
> **Scratchpad 就是记忆追踪系统的实现方式之一**，后续的各个模式中，我们会深入讲其具体实现。

### 8.2 五段式追问清单

> 出了问题，你还需要一套能顺着追下去的清单：

```
1. 这次任务到底要它做什么
2. Agent 最后错在哪一步
3. 正确做法依赖哪一段过去的经验或判断
4. 这段经验，当时有没有被写进记忆
   - 如果写了，这次为什么没被召回：没命中、被淘汰，还是召回后和场景对不上
   - 如果没写，是哪个环节本该写却没写
5. 下一版，你会怎么改记忆 pipeline
```

> 这套追问的目的，是把"Agent 怎么又犯蠢了"拆成一条**可定位的链路**：

```
should_write
       ↓
memory.write
       ↓
memory.retrieve
       ↓
memory.use
       ↓
avoid_repeat_failure
```

### 8.3 链路每一环可能出的问题

| 环节 | 出问题归类 |
|------|------------|
| **没有写入** | **沉淀问题** |
| **没有取回** | **检索问题** |
| **取回不用** | **推理或规划问题** |
| **用了还错** | **记忆质量或适用边界问题** |

> **每一环都可能出问题**。

## 九、感知 vs 记忆的边界

### 9.1 黄佳的明确回答

>
> 还记得上一个模式组开头，我提过一个问题：**感知和记忆都属于 Context Engineering，为什么还要拆成两组**？

| 维度 | 感知 | 记忆 |
|------|------|------|
| **关心的是** | **空间** | **时间** |
| **具体问题** | 这一轮会话里，Agent **看到了什么** | 当前窗口关掉之后，怎么把有用的东西**沉淀下来** |

## 十、记忆攻击：新形态的安全风险

### 10.1 来自《记忆碎片》的最后隐喻

> 最后，再往深一层琢磨《记忆碎片》这部电影，让人后背发凉的不只是"**人会忘**"，而是"**外部记忆也可能被自己利用来欺骗自己**"。
>
> 当线索被**选择性记录、被错误解释**，甚至被**故意篡改**时，**记忆不再是通向真相的路径，反而会变成制造幻觉的机器**。

### 10.2 对 Agent 系统的提醒

> 这对 Agent 系统也是一个提醒：
>
> **记忆不是只要存下来就可靠**。
>
> - **写入什么**
> - **谁有权改**
> - **什么时候过期**
> - **下次如何召回**
> - **召回之后是否真的被用上**
>
> **都需要设计**。

### 10.3 三种记忆攻击

> 否则，未来的 Agent 攻击**很可能不只是提示词注入（prompt injection）**，还会包括：

| 攻击类型 | 含义 |
|----------|------|
| **记忆注入（memory injection）** | 攻击者**直接把错误线索写进外部记忆** |
| **记忆投毒（memory poisoning）** | **污染 Agent 对用户、项目、历史任务**的理解 |
| **记忆篡改（memory tampering）** | **修改已经存在的记忆** |

> 攻击者**不急着骗过这一轮 Agent**，而是先把错误线索写进它的外部记忆，污染它对用户、项目和历史任务的理解。
>
> **等到下一轮 Agent 取回这些记忆时，它会以为自己拿到的是"过去验证过的经验"**，于是非常自然地沿着错误方向继续行动。

### 10.4 终极定义

> **记忆模式是在设计一套可以被追踪、被审计、被纠错的经验系统**。

### 留言 1：街角·陌路△ — 记忆是短期修补 vs 长期工程方案？

> **这里面有一个根本性问题**：记忆这种东西到底是一个**短期内的修补方案**，还是**长期都需要的一个工程化方案**？
>
> 这里边核心的区别就是大模型如果窗口足够大，是不是记忆就不需要了？
>
> 我之前和一个博主讨论，他认为是前者，而**我个人认为后者**，我自己也写了篇文章阐述这个观点，不知道佳哥如何看？
>
> 为论证我的想法，我举一个例子，用的是**博尔赫斯写的《博闻强记的富内斯》**：
>
> 一个叫富内斯的人，从马背上摔下来之后，获得了一个在旁人看来惊人的能力 —— **他可以记住所有事**。
>
> 听起来是天赋对吧？但对富内斯来说，这简直是灾难。
>
> 因为记住所有事，意味着他对所有事没有分类判断。正常人看到两条狗，会觉得这就是两条狗。但富内斯不一样 —— 一条狗背上有黑色绒毛，另一条狗耳朵上有灰色绒毛，一只稍微瘦一些，另一只稍微胖一些。他会把这些差距记得详详细细，而在他眼里，这是**两个完全不同的东西**。他没办法把这两个东西抽象成"狗"。

## 十二、思考题

### 题 1：结构化记忆 vs 摘要记忆实验

> 拿自己的项目做一个简单实验：
>
> **让同一个 Agent 跑同一个长任务，一次给它完整的结构化记忆，一次只给它一行摘要，看看两次成功率差多少**。

### 题 2：Memory Trace 5 段式归因

> 回想一次 **Agent 表现不稳定、反复犯错**，或者**交接后走偏**的场景。顺着 **Memory Trace** 问一遍：

| 步骤 | 问题 |
|------|------|
| 1 | 这次行动**需要依赖哪段过去经验**？ |
| 2 | 这段经验**当时有没有被写入**？ |
| 3 | 如果写了，**为什么没被召回**？ |
| 4 | 如果召回了，**为什么没被用上**？ |
| 5 | 这个问题**该靠改 prompt 解决，还是该靠补记忆链路解决**？ |

### 题 3：十类信息的记忆分类

> 挑一个你正在做的 Agent 项目，列出它现在会接触到的**十类信息**，比如：
>
> 用户偏好、项目规则、任务进度、失败记录、工具返回、临时推理、代码约束、接口文档、历史对话、业务指标。
>
> 然后**给每一类信息标注**：

| 处理方式 | 含义 |
|----------|------|
| 只留在 context window | … |
| 先放 scratchpad | … |
| 写进长期记忆 | … |
| 写进失败日记 | … |
| 应该过期淘汰 | … |

> **这三个问题的目的是启发我们思考**：我们的系统是否已经有记忆需求，但我们尚未发现，或者是把记忆的需求混淆成了其它问题。
