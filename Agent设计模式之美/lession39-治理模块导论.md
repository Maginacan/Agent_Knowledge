# 36｜治理模块导论：把边界写清楚，才敢把事交出去

> **核心命题**：治理在**运行时**分配行动权：把具体提案交给策略裁决，为错误设置硬上限，让权限随可核验结果变化，并保存能够还原责任的运行记录。
>
> **一句话**：既要给 Agent 做事的空间，也要看住这段空间的边界。
>
> 模块围绕薪酬结算，回答四个问题：① 这笔钱能不能付？② 出了错会影响多大？③ 什么时候可以让它自己多做一点？④ 事后能不能查清经过？

---

## 一、释题：管孩子的比喻

讲治理时经常用管孩子举例子。

给他屏幕时间每天两小时，一小时看视频，一小时玩游戏。在这条边界里面，他自己安排——有时把一小时拆成三个 20 分钟，有时拿游戏时间换视频时间，还会提出做家务换几分钟。

这条规则带来了想要的东西：他开始学习怎样分配时间，也有了选择。**有规则让我轻松多了，而且还在可控范围内增加了一些他的自由**。

不过规则同时留下了协商空间：

- 多看 5 分钟似乎问题不大。
- 下一次再多 5 分钟也有理由。
- 每一次单独看都说得过去。
- **连在一起却可能慢慢偏离"学会管理时间"这个目标**。

> **Agent 治理也有这层麻烦**：
> - 人如果每一步都要点头，Agent 就只剩下自动填表。
> - 系统如果只看眼前这一笔调用，一串分别合规的动作，合起来又可能越界。
> - **既要给它做事的空间，也要看住这段空间的边界**。

## 二、当 Agent 开始替人做事

传统软件也会在运行时做选择：读输入，进入某个分支，再调用一个函数。大部分选择空间已经由工程师写在代码里，能沿着分支逐条检查。

Agent 把更多具体选择推迟到了运行时。模型看到当前上下文以后，才决定用哪个工具、带什么参数、按什么次序组合。API Key 把调用关联到某个账户或应用，RBAC 规定这个角色可以使用哪些接口。**但单靠这些信息，还回答不了**：这一位员工、这一笔金额、在这个时间点，究竟该不该付？

### 客服 Agent 100 元优惠券的三个治理问题

假设客服 Agent 准备给一位用户发 100 元优惠券。动作很小，却已包含三类治理问题：

1. **能否放行**——当前工单是否满足补偿条件，金额是否在权限内，这次操作需不需要人看。
2. **怎样追责**——事后要能找到用户请求、Agent 提案、采用的策略、审批结果、工具返回值和业务系统的实际变化。
3. **最多影响多少**——即使判断错了，也只能影响这一张工单，不能顺手修改全站补偿规则，更不能因为重试连续发出十张券。

三件事分别关注**准入、证据和损失范围**。治理还要处理时间——Agent 今天积累的成功记录，是否足以换取明天更大的操作空间。于是又多出第四个问题：

4. **权限怎样增长，又怎样在事故后收回**。

> 把四个问题放在一起，治理就有了可落地的定义：
>
> **Agent 治理**是**在运行时分配行动权**：把具体提案交给策略裁决，为错误设置硬上限，让权限随可核验结果变化，并保存能够还原责任的运行记录。

## 三、先看一条悄悄变宽的现金线

回到薪酬 Agent，看同一份结算数据，为什么只改一个限额，检查结果就变了。

六月月末的测试账本：798 张工资单标为已付款，另外 2 张已冲正，形成一份总额为 **13,706,097 元** 的结算清单。程序用两条规则检查它，其中一条是全款允许自动通过的金额上限：

```text
== scene 2: the quiet widening (June claim 13,706,097) ==
   limit 13,000,000 -> escalated
      refusal names the policy: limit=13000000 observed=13706097.0
   limit 30,000,000 -> accepted
      policy marks on the acceptance receipt: []
```

- 上限 **13,000,000 元**时，清单需要转交人工（`escalated`）。
- 上限放宽到 **30,000,000 元**后，同一份清单就通过（`accepted`）。

> **同一份 1370 多万元的工资清单，按原来的规定超过 1300 万元就要找人审批。实验中把限额提高到 3000 万元，系统就自动通过了**。但放行记录没有记下采用的规则版本，事后只知道"通过了"，却说不清"按什么规则通过的"。

这也许是公司为一次补发工资临时批准提高结算限额——没问题。但这段旧实现只在超限回执中写下触发的金额上限，**放行回执没有写清新的策略版本**。批准之后并不知道采用的是哪一版规则，也无法据此查清谁提出了放宽、谁批准、为何调整。

运行实验：

```bash
python3 governance/payroll-lab/ungoverned_policy_lab.py
```

> **拦下来的时候，系统说得出哪条规则拦了它。放过去以后，规则反而从记录里消失了**。

## 四、把提案、策略和裁决分开保存

现在给每版规则编号：第一版限额 1300 万元，第二版 3000 万元。每次检查结束，系统除记录"通过"或"转交人工"，还要记下使用的规则编号和版本。

> 模式实现将**提案、策略和回执分开保存**（参考 `governance/boundary_contract.py`）。

```python
from dataclasses import dataclass
from typing import Literal

RiskLevel = Literal["low", "medium", "high", "critical"]
Reversibility = Literal["reversible", "irreversible", "compensable"]
ControlDecision = Literal["accepted", "escalated", "rejected"]

@dataclass(frozen=True)
class ActionProposal:
    proposal_id: str
    version: int
    contract_digest: str
    artifact_id: str
    artifact_digest: str
    requested_by: str
    action: str
    resource_scope: tuple[str, ...]
    idempotency_key: str
    risk: RiskLevel
    reversibility: Reversibility

@dataclass(frozen=True)
class PolicyRef:
    policy_id: str
    version: int
    content_digest: str

@dataclass(frozen=True)
class GovernanceReceipt:
    receipt_id: str
    control: str
    proposal_digest: str
    policy_digest: str
    decided_by: str
    decision: ControlDecision
    issued_at: str
```

三个对象的职责：

| 对象 | 保存 | 比喻 |
| --- | --- | --- |
| `ActionProposal` | 准备做什么——绑定任务契约、结算工件、动作范围和幂等键 | 申请单 |
| `PolicyRef` | 按哪一版尺度判断 | 规则版本 |
| `GovernanceReceipt` | 谁在什么时间作出了什么裁决 | 处理回执 |

摘要是根据内容算出的一串校验值。**回执会记下当时提案和策略的摘要**。执行入口准备付款时，还要重新核对：

> "眼前的提案和当前生效的规则，是否与回执对应。"

**金额、收款对象或策略版本变了，就需要按新内容重新判断**。

财务人员事后问："这份清单超过了原来的 1300 万元，怎么还能通过？"——就能查到：**这次采用的是限额 3000 万元的第二版规则**。再查这版规则，就能看到负责人和修改原因。

> 这个实验增加的，就是让每一次放行**都有规则可查**。它还没有证明规则改得合理，也没有证明修改经过了有权审批的人同意。

接下来是第二个问题：**谁有权修改规则**？比如 Agent 想把限额从 1300 万元提高到 3000 万元，不能自己提出、自己批准，必须交给有审批权的人确认。

```text
== scene 3: pin the policy, the change signs its own name ==
   v1 (13,000,000) digest=6ed30edae74d44ab -> escalated
   v2 (30,000,000) digest=0ab3a7e0a7acf1b3 -> accepted
   four-eyes: policy 'cash-line' v3: proposer and approver are the same actor
```

系统通过检查时，也记下了采用了哪版规则。实验还加了**一道检查：四眼原则**——把限额从 1300 万元提高到 3000 万元，提出修改的人不能自己批准自己。如果有人把自己同时填成提出者和批准者，程序就会报错。

> **不仅付款需要审批，放宽付款规则也需要审批**。
>
> **付款前重新核对回执**：提案金额或对象改变后，旧回执的摘要对不上，执行入口拒绝付款。

## 五、四个问题，四种模式

把薪酬结算交给 Agent，还需要回答四个问题：

| 问题 | 谁来回答 |
| --- | --- |
| 这笔钱能不能付？ | 下一讲：**审批门** |
| 出了错会影响多大？ | 下一讲：**爆炸半径** |
| 什么时候可以让它自己多做一点？ | 下一讲：**渐进承诺** |
| 事后能不能查清经过？ | 下一讲：**可观测性** |

### 为什么分成四种模式？

> 因为这些规则经常需要**分别调整**。

比如公司临时提高了某个月的结算额度，并不意味着 Agent 从此可以自行批准大额付款。**预算变了，审批人的责任和 Agent 的权限仍要分别确认**。

分开设计后，能说清楚：

- 这次到底改了什么
- 哪些约束必须继续有效

> 代码和测试也围绕这些具体问题展开——**改额度时检查额度，改权限时检查权限，再验证它们能否一起守住业务要求**。

> **ADPS 版本说明**：本专栏沿用写作阶段形成的四讲结构，把可观测性放在治理模块中收束。ADPS 共同体在后续研讨中调整了目录——把 G1 审批门、G2 爆炸半径控制和 G3 渐进承诺保留在治理行，把可观测性调整为 X1 横切工程面，用来贯穿全部模式和生命周期。这里保留原有教学编排，最新分类与编号以 ADPS 模式目录为准。

## 六、控制面分工

| 主体 | 职责 |
| --- | --- |
| **策略** | 负责判定 |
| **执行层** | 只消费当前有效的回执、额度和权限凭证 |

> **边界越清楚，日常打断越少**。

如果我们没有说清楚哪些事可以交给 Agent，它就只能不断来问。人被问得多了，也容易从认真审批变成随手点"同意"。**所以治理要先分清两类事情**：

- 哪些可以让它自己完成
- 哪些必须停下来找人确认

## 七、2026 年主流框架的安全设计

### OpenAI Codex（2026-05）

介绍内部 Codex 的安全设计时区分了**沙箱**和**审批策略**：

- **沙箱**：限制它能访问哪些文件、能否连接网络。
- **审批策略**：决定哪些操作需要人确认。

### Claude Code

提供权限设置，以及工具执行前的检查机制。这些工具能把检查放进执行过程，但**具体检查什么，还得由业务方决定**。

> 比如，允许 Agent 使用付款接口，并不代表它提出的每一笔付款都应该执行。工资有没有核对过、这笔钱是否已经付过、金额变化后要不要重新审批，**都需要薪酬系统自己判断**。

### 新加坡 IMDA Agentic AI 治理框架（2026-01）

把**技术控制**和**人的责任**放在一起讨论：

- 事前评估风险
- 明确哪些环节需要人负责
- 在开发和运行过程中持续检查
- 让使用者了解系统的能力、限制和操作责任

> 对企业来说意味着：**既要把检查写进程序，也要让人知道自己什么时候该接手、接手后需要判断什么**。

## 八、从教学 Repo 到生产系统

本模块使用固定的样例数据和本地 SQLite 数据库。每次从相同的起点运行，就能看清：改了一条规则以后，检查结果、批准记录和预算余额发生了什么变化。

实际业务还需要考虑：

### 五条生产化要求

1. **确认是谁在操作**——用户、Agent 和审批人的身份，要从可信的登录与身份系统中取得，不能由程序随便填个名字。
2. **查得到规则的来历**——当前限额是多少、什么时候生效、谁提出修改、谁批准，都要保存下来，旧版本也不能直接抹掉。
3. **真正付款前必须检查**——最终执行付款的程序，要核对申请内容、审批结果、剩余额度和当前权限，不能只在前面的页面上检查一次。
4. **分清钱付到了哪一步**——记录哪些款项已经支付、哪些尚未支付、哪些暂时查不到结果。**银行请求超时后，要先查清有没有付成，不能直接再付一遍**。
5. **出事后查得清，也停得下**——保留经过脱敏的操作记录，并提供**不依赖 Agent 自己决定的停止手段**，及时阻止后续操作。

### 自查方法

> 检查自己的系统时，可以从"**真正提交付款**"的那段代码往回看：它执行之前，到底检查了什么？
>
> **如果"超过限额必须审批"只写在提示词里，付款程序却不检查批准记录，这条要求就还没有真正落实**。

## 九、总结

给孩子两小时屏幕时间，是希望他在这个范围内学会自己安排。如果规则被一次次放宽，最后偏离了原来的目的，我也需要介入。

把任务交给 Agent，同样要说清楚：

- **哪些决定可以交给它**
- **哪些仍然需要人确认**
- **交出去以后还要知道它实际做了什么**
- **什么时候应该收回权限**

> 后面四讲沿着薪酬结算这个例子，逐一讨论审批、损失范围、权限调整和运行记录。每一讲都解决一个具体问题，让"放心交给它"有可以检查的依据。

## 十一、思考题

1. 你的系统记录"通过"时，**能不能查到当时采用了哪一版规则**？
2. 如果有人要提高付款限额，应该由谁批准？现有记录能否查到**修改前后的数值和修改原因**？
3. 找到系统里**真正执行付款、删除数据或对外发送消息的代码**。它执行前检查了什么，又有哪些要求只写在提示词或文档里？
