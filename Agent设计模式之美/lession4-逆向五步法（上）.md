## 上一讲回顾与本讲定位

通过前面三讲，我们已经完成了**范式觉醒模块的两块地基**。

- **第 1 讲**说清楚了为什么旧词汇不够用。GoF 假设结构性决策由人类工程师在设计期完成；Agent 系统把一部分决策搬到运行期、搬到模型手里，于是我们必须重新设计 Harness，让模型在不确定性里被约束地行动。
- **第 2、3 讲**建立了双轴坐标系。纵轴是认知功能，横轴是执行拓扑。一个模式必须同时回答 Agent 在做什么和数据怎么流。有了双轴，模式才有坐标、边界和失败模式。

> **今天这一讲要补上第三块地基：怎么看懂真实工业系统。**

比如我们打开一个 50 万行的 Agent 工程仓库，还是不知道从哪里下手，那些概念就停留在白板上。**工程师真正要练出来的能力，是把一个陌生系统拆成可验证的结构图。**

这就是**逆向五步法**。其实也就是通过 5 个具体步骤来做逆向工程，剖析成熟的 Harness 框架。

```text
Detect / Classify / Filter / Map / Verify
找主循环，分组件，滤噪声，落矩阵，源码验证
```

## 为什么是这 8 个框架

今天会用 **8 个 Agent Harness** 当样本：**Claude Code、Codex CLI、Aider、OpenCode、OpenClaw、Hermes Agent、DeerFlow、OpenHands**。

> **8 个框架只是素材。真正的主角是庖丁用来解牛的那把刀。我们是用这把刀来对市场上的各种 Harness 进行横切。**
>
> **8 个框架会变，版本会变，目录结构也可能变。但只要 Agent 还需要感知、记忆、推理、行动、反思、协作和治理，逆向五步法就仍然适用。**

### 选样的三原则

选样本不能全按热度榜来，也不能把 GitHub Trending 上的项目挨个讲一遍。一个好的横切面至少要覆盖三件事。

**第一，要覆盖不同主战场。**

- 代码 Agent
- 个人助手
- 多 Agent 编排
- 沙箱执行

代码 Agent 最怕看错仓库、改错文件；个人助手最怕身份、权限和长期记忆失控；多 Agent 最怕任务拆开以后收不回来；沙箱执行最怕"能做事"变成"乱做事"。如果只看其中一类，很容易把局部经验误当成通用规律。

**第二，要覆盖不同工程姿态。**

- 闭源产品
- 商业公司主导的开源项目
- 社区驱动项目

大公司会把治理、权限、协议和可运维性做得更重；社区项目常常在一个关键不变量上打得很深。

> 比如 **Aider** 的关键价值，已经超出"它能帮你改代码"这层功能描述。它抓住了 **Git 这个核心不变量**：所有修改都可以通过 diff、commit、rollback 被审计和控制。
>
> **OpenCode** 也类似，它抓住了 **LSP** 这个核心不变量，Agent 可以借助 IDE 的语言理解能力，理解定义、引用、诊断和符号结构。
>
> 前者说明代码 Agent 必须进入版本控制系统，后者说明代码 Agent 必须进入开发环境本身。

**第三，要覆盖不同的"2026 变量"。**

2026 年的 Agent Harness 已经走过了工具调用演示阶段，开始呈现出更完整的系统工程形态。

| 2026 变量 | 解决什么问题 |
|---------|------------|
| **运行形态** | Agent 不再只是网页聊天框，而是 CLI / IDE 插件 / 桌面应用 / 本地可执行 |
| **协议与连接层** | JSON-RPC、LSP、local-first gateway，让 Agent 稳定通信 |
| **经验沉淀层** | procedural skills，把一次次任务的做法沉淀成可复用流程 |
| **执行与隔离层** | sandbox、权限控制、本地确认机制，防止 Agent 失控 |
| **可观测与审计层** | event replay、trace、日志、状态账本，让 Agent 行动可回放 |
| **协作边界层** | 子 Agent 职责、权限、上下文范围、交接边界是否清楚 |

> 也就是说，**Agent 工程正在从"模型会不会调用工具"转向"模型如何被放进一个可靠运行时"。**

8 个样本放在一起，刚好形成一个坐标系：左边是开发者工作流，右边是个人与组织工作流；整体上既包含感知和记忆，也有行动和治理，同时用协议、事件、沙箱、权限把模型的不确定性包起来。

> **产品很快过期，而标本背后的工程理念却能长存。我们真正要学的是它们为什么这样设计。**

## 为什么需要"逆向五步法"

读 Agent 框架源码经常会掉进一些坑。

### 第一个坑 · README 幻觉

README 通常告诉你这个项目"能做什么"，但很少告诉你它"为什么这样做"。你读完以后，可能知道它支持工具调用、支持多 Agent、支持沙箱执行，但你仍然不知道：

- 主循环在哪里？
- 状态怎么传？
- 上下文怎么装配？
- 权限在哪里被卡住？

**我们看到了功能清单，却没有看清系统骨架。**

### 第二个坑 · 关键词漫游

很多人一上来就开始 grep：agent、tool、memory、context。结果跳出来几百个文件，每个文件看两眼，都像是重点。看了一圈以后，脑子里只剩下一堆碎片。

**你以为自己在逆向架构，其实只是在源码景点观光打卡。**

### 第三个坑 · 从入口函数一路钻到底

大型项目里，70% 的代码可能都是配置、日志、类型定义、序列化、适配器、UI glue、兼容层。你从 `main()` 开始顺着调用栈往下钻，很容易钻进一条很漫长但不关键的支路。

**费了半天劲，文件看了很多，却忘了自己最初到底想找什么。**

### 真正的卡点是缺少预期框架

> **逆向工程的第一原则是：先知道一个 Agent Harness 理论上应该长什么样，再去源码里验证它实际什么样。**

没有预期框架，源码阅读就是信马由缰；有了预期框架，源码阅读才能按图索骥。

那么，一个 Agent Harness 理论上应该长什么样？其实它的骨架很稳定：

1. **一定有一个主循环**，负责接收输入、装配上下文、调用模型、处理工具结果，并决定下一步怎么走
2. **一定有上下文管理**，否则 token window 很快就会失控
3. **一定有工具注册和调度**，否则模型的行动空间就没有边界
4. **一定有某种状态或事件记录**，否则长任务无法恢复，出了问题也没法调试、回放和审计
5. **一定有治理边界**，哪怕很弱，也会以权限、沙箱、确认、日志、策略等形式出现

> **逆向五步法，就是把这五个预期变成一套可执行流程**：先找主循环，看 Agent 如何一轮一轮推进；再找上下文管理，看它如何控制模型看到什么；再找工具系统，看行动空间如何被注册、约束和调度；再找状态与事件记录，看系统如何支持恢复、调试和审计；最后找治理边界，看权限、沙箱、确认和日志在哪里真正生效。

**问题也从"这个项目有多少功能"，变成：它把模型放进了一个怎样的运行时？**

## 逆向工程五步法详解

前面已经搭好了"认知功能 × 执行拓扑"这张矩阵。但矩阵本身只是工具。**真正关键的是：我们能不能拿它去拆解真实的 Agent 框架源码？**

把这个过程提炼成五步：

```text
1. Detect  探测 —— 先找主循环
2. Classify 归类 —— 把组件归到七脉
3. Filter  降噪 —— 主动丢掉 70% 噪声
4. Map    映射 —— 落到双轴矩阵
5. Verify 验证 —— 回到源码验证判断
```

这五步做完，一个原本很复杂的 Agent 框架，就会从"一大堆文件"变成一张你能看懂、能比较、能讲清楚的结构图。

### Step 1 · Detect · 先找主循环

**所有 Agent Harness 都有一个心脏。** 这个心脏通常藏在一段不断重复的运行循环里，未必是 README 里最显眼的概念，也未必是项目里最有名的类。

这个循环大概长这样：

```text
用户输入
  -> 构造上下文
  -> 调用模型
  -> 解析模型返回
  -> 分发工具 / 交给其他 Agent / 询问用户
  -> 收集执行结果
  -> 更新状态
  -> 继续下一轮，或者停止
```

英文版本：

```text
input
  -> build context
  -> call model
  -> parse response
  -> dispatch tools / handoff / ask user
  -> collect observations
  -> update state
  -> continue or stop
```

> **找到这段循环，就等于抓住了系统的脊柱。** 找不到它，所有组件都是散的。

#### 第一步要回答的三个问题

1. **用户输入从哪里进来？**
2. **LLM 调用在哪里发生？**
3. **工具执行结果怎么回到下一轮上下文？**

#### 实操：grep 关键词

```bash
rg "tool_call|function_call|tool_use|ToolCall|Action|Observation" .
rg "while|loop|step|run|turn|conversation|session" .
rg "messages|context|history|state" .
```

然后顺着两个方向交叉定位：

- **一个方向是入口**：用户输入、session、conversation、turn
- **另一个方向是模型调用**：messages、model、completion、response、tool call

> **真正的主循环，通常会同时碰到三件事：messages、model call、tool dispatch。** 只处理 UI 的文件大概率可以排除；只处理配置的文件也先放一边；某个具体工具的实现，通常只是主循环调用的一环。

这一阶段的产出物，不需要精细。你只需要画一张很粗的图，**最好不要超过 10 个框**：

```text
User Input -> Session -> Context Builder -> LLM -> Tool Dispatcher
               ^                                  |
               |                                  v
             Event Log <- Observation <- Runtime / Sandbox
```

**抓大放小。**

### Step 2 · Classify · 把组件归到七脉

找到主循环之后，**不要急着继续往下钻**。正确做法是：先停一下，用上一讲的"认知七脉"对号入座，给主循环周围的组件做归类。

> **这个组件到底在帮 Agent 管什么资源？**

| 问题 | 归类 |
|------|------|
| 它是在决定 Agent 看见什么？ | **Perception** |
| 它是在决定 Agent 记住什么？ | **Memory** |
| 它是在组织推理步骤？ | **Reasoning** |
| 它是在执行工具和外部动作？ | **Action** |
| 它是在检查、修正、重试？ | **Reflection** |
| 它是在拆分任务、调度子 Agent？ | **Collaboration** |
| 它是在管理权限、审计、沙箱和边界？ | **Governance** |

#### 注意：不要只看名字，要看它真正做什么

- **Aider 的 repo map**：名字看起来像仓库索引，实际决定哪些代码结构能进入 LLM 上下文 → **首先归 Perception**；同时让 Agent 对整个仓库形成压缩后的持续认识 → **带一点 Memory**
- **OpenHands 的 Event System**：表面看是日志，实际是事件账本，把 Agent 状态变成可追加、可回放的事件 → **既是 Memory，也带 Governance**（过程可追踪可审计）
- **Claude Code 的 Subagent**：当然是 Collaboration，但每个子 Agent 有自己的上下文 → **相当于把不同任务的观察范围隔离开**，所以也带 Perception 作用

> **一个组件可以跨多脉，但是第一遍不要太精细。先给每个组件找一个主脉，再在旁边标注副脉就可以。**

### Step 3 · Filter · 主动丢掉 70% 噪声

> **读大型工程最反直觉的能力，是敢于不读。**

大型 Agent Harness 里面，有大量代码很必要，但**第一轮逆向不用先看**：

- CLI 参数解析
- UI 布局
- 错误文案
- telemetry 上报适配
- schema 类型定义
- provider SDK 包装
- serialization / deserialization
- 测试 fixture
- 平台兼容性分支

#### Filter 阶段的判断标准

> **这个文件会不会改变 Agent 的决策、上下文、状态、行动或权限？如果不会，先标成 boilerplate，暂时放一边。如果会，再继续问：它改变的是哪一类东西？**

- 改变 Agent **看到什么** → Perception
- 改变 Agent **记住什么** → Memory
- 改变 Agent **怎么想** → Reasoning
- 改变 Agent **能做什么** → Action
- 改变 Agent **怎么纠错** → Reflection
- 改变任务**由谁来做** → Collaboration
- 改变**边界、权限和账本** → Governance

#### 8 个框架的过滤优先级

| 框架 | 优先看 | 暂时跳过 |
|------|-------|---------|
| **Claude Code** | 工具注册、工具执行、权限、AgentTool、context 装配 | UI |
| **Codex CLI** | core、protocol、sandboxing、exec policy | 每个 crate |
| **Aider** | base_coder.py、repomap.py、repo.py | 各种 prompt variant |
| **OpenCode** | session、llm agent、permission、lsp | UI/TUI 只看它如何触发会话和权限 |
| **OpenClaw** | gateway、channels contract、workspace、memory-host-sdk、skills 文档 | — |
| **Hermes Agent** | run_agent.py、hermes_state.py、memory_setup、skills_hub、gateway | 每个 CLI 命令 |
| **DeerFlow** | agent router、skill router、memory router、sandbox tests、subagent tests | 测试文件在这里很有价值，因为它们暴露了系统边界 |
| **OpenHands** | event service、sandbox service、conversation service、runtime README | 前端和集成模板 |

> **Filter 过程做得好，读源码速度会突然快很多。** 咱得知道哪些地方现在必须读，哪些地方以后再说。

### Step 4 · Map · 落到双轴矩阵

前三步之后，你已经知道主循环在哪里、组件属于哪几脉、哪些文件暂且放过。第四步开始进入这门课的核心——**把组件落到 7 × 6 的正交模式矩阵**。

#### Map 不能变成贴标签

> **看到功能就随手写"这是 Memory"，看到工具调用就写"这是 Action"，这还不够。真正的 Map，是把一个框架变成可以比较的工程对象。**

这一步需要逼自己说清楚：**一个功能到底是哪个功能，采用哪种拓扑，失败模式是什么。**

#### 例子：OpenHands EventLog

如果只是看 OpenHands 有 EventLog 只是一个事实。但**把它落到矩阵里，它就变成了三个工程判断**：

1. **它解决 Memory 问题**，因为系统状态来自一串事件，不再散落在对象内存里
2. **它也解决 Governance 问题**，因为事件可以审计、可以回放
3. **它采用的是 Chain / append-only 的拓扑**，优点是错误不会被悄悄覆盖，缺点是日志会膨胀，replay 成本需要管理

这样你对它的掌握程度，就从"知道一个功能"上升到了"理解一个设计"。

#### 最终产物：热力图

```text
热力图预览（引用请标明出处：极客时间《Agent 设计模式之美》专栏）
```

**这张热力图不需要一开始就百分百精确。** 它的价值是帮你比较不同框架的工程性格。

- **横着看**，能看出一个框架的偏好
  - Aider 很专注，核心围绕代码上下文、编辑和提交
  - OpenHands 更重沙箱、事件和运行时
  - Hermes 更重记忆、技能和用户模型
  - DeerFlow 更重协作、路由和执行环境
- **竖着看**，能看出某个模式的工业普及度
  - Tool Dispatch 几乎所有框架都有
  - Experience Replay 不是每家都有
  - Blast Radius 在 sandbox-heavy 的系统里很强，在普通 dev tool 里可能比较弱
  - Subagent / delegation 在不同框架里的成熟度差异很大

> **这就是矩阵的价值。** 它让你从"我读过这个项目"，变成"我能比较这些项目"。而专栏后面几十讲的主要工作之一，就是带着大家一起完成这张图。

### Step 5 · Verify · 每个判断都要能回到源码

> **没有 Verify，逆向工程就很容易变成讲故事。** 你说这个框架重治理，他说那个框架重记忆，听起来都很有道理，但如果不能回到源码、测试或官方文档，那就只是解释，不是论证。

**Verify 的意思是，我们对一个框架做出的每个架构判断，都要有据可查。**

证据大致分三层：

| 证据层 | 强度 | 用途 |
|-------|------|------|
| **第一层：源码** | 最强证据 | permission 模块、sandbox manager、event store、repo map 实现、tool dispatcher |
| **第二层：测试** | 强力证据 | 暴露设计边界：sandbox 怎么限制动作、Subagent 怎么传递上下文、memory 什么情况下写入 |
| **第三层：官方文档** | 辅助证据 | 确认产品语义和公开承诺 |

Verify 阶段，最好在热力图旁边再放一张引用表。

> **经过了最后这轮 Verify，我们就可以自信地说：这个框架很重治理，因为它在 sandbox provider、permission policy、event store 三个位置都把治理做成运行时机制。这就是工程论证和产品解读的区别。**
>
> **产品解读可以停留在概念层，工程论证必须回到代码层。**

上面这 5 步，做起来要比"让 AI 去分析吧"繁琐得多，但更有价值。**有意识地让我们的思维进行摩擦，通过做"具体的难事儿"来在 AI 时代继续点亮我们的思维火花。**

## 总结

好，到这里，我们就把逆向 Agent Harness 的方法讲清楚了。**读懂几十万行源码的快捷通道，是建立一套看系统的工程方法。**

### 五条要点

1. **读 Agent Harness，不能从 README 和热词开始，而要先找主循环。** 主循环是系统的心脏，它把用户输入、上下文装配、模型调用、工具执行、状态更新串在一起。抓住主循环，系统才不再是一堆散乱文件。

2. **找到主循环之后，要用"认知七脉"给组件归类。** 感知、记忆、推理、行动、反思、协作、治理，不是抽象概念，而是源码里真实存在的控制点。它们分别决定 Agent 看见什么、记住什么、怎么思考、怎么行动、怎么纠错、怎么协作、怎么被约束。

3. **读大型工程，要敢于过滤噪声。** 第一轮不需要读懂所有 CLI 参数、UI 组件、provider 适配和序列化逻辑。真正要抓的是那些**会改变 Agent 决策、上下文、状态、行动和权限的地方**。

4. **Map 的价值，是把一个框架放进双轴矩阵，让它变成可比较的工程对象。** 不只是说"这个框架有 memory""那个框架有 tool"，而是要说清楚：**它解决的是哪个认知功能，采用的是哪种执行拓扑，带来的失败模式是什么**。

5. **所有判断都要 Verify。** 没有源码、测试或官方文档支撑的架构解读，只是讲故事；能回到证据的解读，才是工程论证。

## 思考题

1. **预期 vs 验证**：选一个你熟悉的 Agent 框架，先不要看源码，先写出你预期它一定应该具备的五个地基：主循环、上下文管理、工具注册与执行、状态账本、治理边界。然后再去源码或文档里验证。

2. **主循环图**：拿 Claude Code、Aider、OpenHands、Hermes 任意一个框架，画一张**不超过 10 个框的主循环图**。重点标出：用户输入从哪里进来，模型在哪里被调用，工具结果如何回到下一轮上下文。

3. **组件归类**：找一个具体组件，比如 **repo map、event log、sandbox、permission policy、Subagent、skills hub**，把它归到"认知七脉"里，再进一步落到"双轴矩阵"里。**注意说明：为什么它主要属于这个格子，而不是另一个格子。**
